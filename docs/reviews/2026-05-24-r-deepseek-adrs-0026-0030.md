# Reviewer: DeepSeek-V4-Pro — Math/correctness critique of ADR-0026..0030

## P0 (must-fix — numerical/correctness defect blocking acceptance)

### P0-1: ADR-0027 D3 — covered_call sizing denominator off by 100× and ignores net-premium offset

The ¼-Kelly → contract-count translation groups **covered_call** under "Income / Assignment-Risk" with the formula `contracts = math.floor(abs(target_nav) / (collateral_per_contract))`, where `collateral = current basis of long stock` (ADR-0027 D3, lines 664–670).

**Bug**: The CSP case explicitly multiplies: `collateral = strike × 100`. The CC case does not — it says "current basis of long stock" without `× 100`. If the per-share basis is $145, the denominator is 145 instead of 14,500, producing **100× too many contracts**. Even if the `×100` is implied, the formula has a deeper error: for a covered call *initiated from scratch*, the net capital deployed is `(spot_price − call_premium) × 100`, not the gross stock basis. Using gross basis overstates the denominator, systematically **undercounting** contracts. For a wheel entry (stock already owned), the capital is already deployed — the formula should size *additional* contracts against *available* capital, not re-count the existing basis. This is a three-way classification error: the covered call doesn't share the CSP's denominator logic, doesn't match the directional path's premium-based denominator, and doesn't fit the spread's defined-risk max-loss denominator.

**Proposed fix**: Split CC sizing into two cases — *initiation*: `contracts = floor(|target_nav| / ((spot − call_mid) × 100))`; *wheel overlay*: `contracts = floor(|target_nav| / (call_mid × 100))` since capital is already deployed in the underlying. Both need the explicit `×100`.

### P0-2: ADR-0027 D6 — net-Greeks aggregation silently fails for covered-call stock leg

`aggregate_legs(legs: list[OptionLeg])` (ADR-0027 D6, lines 727–742) iterates over `OptionLeg` objects. A covered call has two legs: **long stock** (not an `OptionLeg`) + **short call** (`OptionLeg`). The stock's delta (1.0 × 100 shares = 100 delta) is **never aggregated** by this function because the stock leg is not an `OptionLeg`. The `evaluate_options_proposal` function then computes `new_portfolio_net = portfolio.net_greeks + candidate_net`, which adds only the option leg's delta (e.g., −30 for a −0.30Δ short call) to the portfolio. If the portfolio net greeks already include the stock position from a prior tick, this works by accident — but only if the stock was already in the portfolio before the proposal. For a fresh CC, the proposal's net greeks are **incomplete**, and the gamma/vega caps (O3, O5) are evaluated against a misleading partial-Greek snapshot.

**Corner case**: Two legs of opposite sign — a bull call spread (buy 0.60Δ, sell 0.40Δ) computes correctly (net 20 delta). The bug is specific to multi-leg strategies containing non-option instruments.

### P0-3: ADR-0028 D4–D5 — parquet replay accepts look-ahead-contaminated greeks

ADR-0028 D5 (lines 1202–1213) mandates `as_of` semantics and the `shuffle_timestamps_test` CI gate. ADR-0028 D7 (lines 1234–1261) records every `fetch_chain` result to parquet. For backtest replay, these parquet files are read directly — **bypassing `complete_greeks` entirely**. The greeks in the parquet file were computed at *record time*. If the recording happened with look-ahead (e.g., a live tick captured chains at 16:00 ET and the parquet writer stamped them with `asof=09:35 ET`), the replay will serve forward-contaminated greeks and the `shuffle_timestamps_test` will never detect it because the test re-generates greeks from bars ≤ T, while production replay reads pre-computed greeks. The prevention mechanism (CI gate) and the production path (parquet read) evaluate **different greek sources**, creating a silent look-ahead channel.

**Fix**: Parquet replay must re-run `complete_greeks` against the stored `(spot, strike, dte, iv)` inputs at replay time, using only the `asof`-filtered market data, or the parquet must record a `greeks_computed_at` provenance that is verified ≤ `asof` at read time.

## P1 (should-fix)

### P1-1: ADR-0026 D1 — Postmortem "current system time" leak in `was_gate_rejection_correct` window

ADR-0026 D1 (lines 117–186) claims the postmortem is deterministic from `signal_bus + execution_bus + market_data`. The `was_gate_rejection_correct` field requires the "would-be hold window" for a gate-rejected trade. The postmortem schema stores `time_to_target_minutes` (line 154) — but this is the *predicted* time horizon from the signal. If the signal's time horizon is null (no target specified), the postmortem code must fall back to a **default hold window** (e.g., "next 60 minutes" or "until end of session"). If that default is computed from `datetime.now()` at write time rather than from `asof_decision + config.default_hold_minutes`, replay produces a different window on different days. The `hold_minutes` field (line 144) is also a candidate — if computed as `(asof_settlement − asof_decision).total_seconds() / 60`, it's deterministic from the two stored timestamps. If either timestamp is missing and filled from `datetime.utcnow()`, it's non-deterministic.

**Fix**: Explicitly derive all time-window parameters from `asof_decision` + recipe config, never from wall clock at write time. Store the hold-window config parameter in the postmortem record so replay is self-contained.

### P1-2: ADR-0029 D3 — NTA ordering non-determinism for same-day multi-leg expiry

ADR-0029 D3 (lines 1512–1521) reconciles NTAs by iterating the `/v2/account/activities` response and emitting `RealizedOutcome` rows. Two NTAs for the same `multi_leg_id` (e.g., short put assigned + long put exercised on the same expiration Friday) may arrive in the same API response in **arbitrary order**. The cash flow from the assignment might be needed to fund the exercise, or the P&L computation might depend on which leg settled first. The ADR does not specify a sort key for processing NTAs within the same `multi_leg_id`. The Alpaca API does not guarantee temporal ordering within a single `/activities` page — two activities with the same `date` may appear in any order. This means replay of the same parquet-captured `/activities` response could produce different `RealizedOutcome` rows if the implementation iterates in insertion order and the hash table iteration order changes across Python versions or process restarts.

**Fix**: Sort NTAs within the same `multi_leg_id` by `activity_type` priority (`OPXRC` → `OPASN` → `OPEXP`) and then by `transaction_time` before emitting outcomes. Record the sort key in the outcome for audit.

### P1-3: ADR-0030 D4 — composition arithmetic: 1-of-3 direction disagreement triggers silence by default, but ADR-0023 committee may override

ADR-0030 D4 (line 1851): "If two methodologies vote opposite directions on the same name, the picker emits no proposal." With three methodologies (A=0.10 long, B=0.15 long, C=short), a **single dissenter silences the name** — consistent with silence-by-default. However, D4 also says the vote "aggregates strictly via ADR-0023's deliberative committee" and the conflict rules apply "at the proposal layer (post-aggregation)." ADR-0023's BMA+stacking committee produces a weighted-aggregate `AnalystView` with a *direction* field. If C's short vote has low confidence or low weight, the committee may still produce a net-long aggregate. The post-aggregation "direction disagreement" rule then checks the *raw methodology votes*, not the committee aggregate. This creates ambiguity: does the rule inspect pre-aggregation votes (any two opposing → silence) or post-aggregation direction (committee says long → proceed)?

**Fix**: Clarify whether D4's direction-disagreement rule fires on pre-aggregation raw votes (cited as ADR-0023 §committee-input validation) or post-aggregation committee output. If pre-aggregation, state that 1-of-N dissenter silences. If post-aggregation, the committee's confidence-weighted output decides.

### P1-4: ADR-0030 D1 — schema drift between YAML namespace and runtime evaluator

ADR-0030 D1 (lines 1708–1790) defines methodology rules in three namespaces: `fundamentals`, `options_chain`, `event_flags`. The runtime evaluator (`Methodology.evaluate`) must resolve e.g., `options_chain.iv_rank` to actual data. The ADR acknowledges broker field naming instability (line 1904) and says "the loader maps to broker-specific names." But the **schema validation** (`schema.py`, line 1948) validates YAML structure only — it checks that `options_chain.iv_rank` has `{min, max}` bounds, not that `iv_rank` exists in the broker mapping table. If a methodology YAML references `options_chain.iv_rank` but the evaluator's resolver maps `options.iv_rank` or `option_chain.iv_percentile`, the rule **silently passes** (field not found → no constraint violated → candidate passes). This is a false-negative in the methodology filter: the YAML author intended a constraint that is never applied.

**Fix**: The schema validator must cross-reference every `must_pass` rule's fully-qualified field name against the active resolver's field registry at load time. If a field name has no resolver, the methodology load must fail with `UnresolvableRuleField(methodology_id, field_path)`, not skip with a warning.

### P1-5: ADR-0028 D3 — py_vollib Black-Scholes for American options produces stale-greek false positives

ADR-0028 D3 (line 1176) acknowledges the European-vs-American approximation gap and proposes flagging contracts with `|moneyness| > 0.10` and `dte < 30`. However, the stale-greek detection (line 1147, 1161) compares provider greeks against a 60-second staleness threshold. For deep-ITM American puts near ex-div, the provider's American-model greeks diverge from py_vollib's European greeks by more than typical market noise. The `complete_greeks` function may **replace a correct provider American delta with a European-approximation delta** because the provider value is "stale" (>60s), and the recomputed value differs materially — yet the `iv_source` is marked `"stale_provider"`, hiding the fact that the replacement value is *less accurate than what it replaced*.

**Fix**: For American-style contracts flagged with the European-approximation caveat, never replace provider greeks with synthesized greeks when `iv_source == "stale_provider"` — keep the stale-but-American value and flag it as `"stale_provider_american_kept"`. Synthesize only when the greek is entirely missing (`None`).

## P2 (nits)

### P2-1: ADR-0026 D7 — cost ceiling arithmetic doesn't scale with postmortem volume

ADR-0026 D7 (lines 347–359) claims $0.24–2.92/mo for the retro loop, independent of trade count. The per-call LLM cost depends on **prompt token count**, which grows with the number of postmortems in the weekly window. At 20 trades/week × ~500 bytes/postmortem = ~10KB of postmortem JSON. Each of three models (Bull, Bear, Synthesizer) processes this. Token cost scales roughly as `O(postmortem_count)`. At 80 trades/week (high-frequency options scalping), the weekly prompt could be 40KB, tripling the per-call cost. The ADR's claim of cost-independence from trade volume is false — it scales linearly with postmortem count per audit window. The $30/month hard cap absorbs this in practice, but the stated range $0.24–2.92 should be qualified with "at ≤20 trades/week."

### P2-2: ADR-0029 D1 — `Decimal` strike in OCC but `float` strike in OptionContract

ADR-0029 D1 (line 1491) uses `Decimal` for strike in `OccComponents` to avoid the `145.005 × 1000 → 145004.999...` rounding hazard. ADR-0028 D1 (line 998) defines `OptionContract.strike: float`. The OCC format/parse round-trip goes through `Decimal` → `str` → `Decimal`, but the `OptionSnapshot` carries `float` strike. Converting `Decimal("145.00")` → `float` → `Decimal` can introduce `145.00000000000003`, breaking OCC round-trip equality. The test plan (ADR-0028, line 1397) asserts `parse_occ_symbol(occ_symbol(...))` equivalence — this test will be **flaky** if it goes through the float path.

### P2-3: ADR-0030 D6 — daily-picker cron lacks explicit HITL-gate passthrough assertion in the flow description

ADR-0030 D7 (lines 1882–1892) describes the cron as `pdrl run --recipe daily-picker`. D6 step 6 says proposals land in `proposal_store`. The posture restatement (line 1704) says "No money flows through the picker." While no HITL-bypass path exists in the spec, the cron's textual description doesn't explicitly restate "→ proposal_store → HITL CLI required" in the D7 cron section itself, creating a documentation-only risk that a future reader might mistakenly wire the cron output directly to the broker adapter. Adding one sentence to D7: "Proposals emitted by this cron require explicit `hermes quant approve` before any broker order is submitted" would close the documentation gap.

## Strengths (what NOT to change)

1. **ADR-0026 D2 — Bull/Bear/Synthesizer isolation with cross-family enforcement.** The adversarial scatter preventing sycophancy is the strongest structural guarantee in the bundle. Bull and Bear never see each other's outputs; the three-family diversity requirement with hard-fail (no same-family fallback) is correctly specified and testable (line 497).

2. **ADR-0027 D5 — Kill-switch scope isolation per ADR-0009 §P1-9.** Gamma-spike halt on AMD does not halt NVDA strategies. The `(account, asset_class, symbol?)` scoping is precise and the "no auto-clear from successful trade" invariant (line 721) prevents silent re-arm bugs.

3. **ADR-0029 D6 — Atomic HITL approval with type-level partial-approval prevention.** Making partial leg approvals unrepresentable at the schema level (`PartialApprovalForbidden`, line 1577) is the correct defense against the "approve short call, reject stock buy → naked short" class of bug. This is a correctness-by-construction pattern.

4. **ADR-0030 D3 — From-reel dual-branch extraction with diff.** Running traditional (Whisper+OCR) and multimodal (Gemini) branches blind, then diffing for convergence, is a well-structured defense against single-model extraction errors. The `STATED` / `INFERRED` / `INFERRED-NUMERIC` confidence annotation on every rule provides an auditable provenance trail.

5. **ADR-0026 D4 — `evidence_postmortem_ids` immutable link.** Connecting amendments to specific trade IDs (line 287) creates a non-rewritable evidence chain. If those trades are later flagged as anomalous, the amendment's evidence is automatically weakened in the next monthly retro — a built-in self-correction mechanism.

## Verdict

**CONDITIONAL ACCEPT — P0 issues must be resolved before ADRs are accepted.**

P0-1 (CC denominator off by 100×) and P0-2 (stock leg missing from Greek aggregation) are correctness defects that would produce silently wrong position sizing and risk evaluation on the very first covered-call trade. P0-3 (parquet replay bypasses greek recomputation) is a look-ahead channel that would corrupt backtest results and erode the no-look-ahead CI gate's validity. These three are blocking. P1 issues are important but have workarounds or are unlikely to manifest in the initial 30-day paper window. P2 nits are documentation/clarity improvements.

The architectural posture — adversarial scatter, atomic HITL, proposal-only output, capital-at-risk sizing — is sound. The implementation details need the math corrections above before the options pipeline is trustworthy against real money.
