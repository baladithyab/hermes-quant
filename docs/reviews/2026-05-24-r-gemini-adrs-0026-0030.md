# Reviewer: Gemini-3.1-Pro — Cross-family critique of ADR-0026..0030

## P0 (must-fix — blocks acceptance)
- **Arbitrary Code Execution via Retro Loop (ADR-0026 D5):** D5 states the retro loop can output `code_change` to be applied via `git apply`. Even with `$EDITOR` or human review, allowing an LLM to generate arbitrary unified diffs and prompting the user to apply them circumvents the entire structure of the system's hard rules. A human approving a complex diff is highly prone to silent rule violations. If the system is meant to be configurable, those configurations must be lifted to data (YAML/JSON) where the schema enforces constraints (e.g., parameter ranges). Propose: Remove `code_change` from `scope_type` (ADR-0026 D4/D5). The retro loop may only tune parameters or analyst weights.
- **Race Condition in `is_paper` Check (ADR-0029 D7, Implementation Sketch):** The check for `account.is_paper is False` happens at `submit_mleg_order()`. If `account` is mutable or if a paper account can be flipped to live mid-flight by a configuration drift in the environment, this check is racy. Furthermore, blocking multi-leg purely on an assumed `is_paper` boolean means a staging environment misconfigured as `paper=True` when it has real credentials will execute live multi-leg orders. Propose: The protection must be stronger than checking a boolean. The broker interface interface itself must be typed such that a `LiveBroker` class physically cannot accept a `MultiLegProposal` until explicitly refactored during the "Live Multi-Leg Promotion" ADR phase.
- **Non-determinism in Counterfactual Gate Rejection (ADR-0026 D1):** D1 states `was_gate_rejection_correct` is deterministic because it computes the would-be hold window "from realized bars". However, options fill prices are path-dependent. If the option bid/ask fluctuated inside the bar, and the execution is simulated on later data, whether it would have hit the stop loss or profit target before expiration is non-deterministic (it depends on intra-bar assumptions). P&L attribution on skipped trades cannot be deterministic without tick-level data, which the system does not seem to guarantee it retains. Propose: Explicitly define the counterfactual execution heuristic (e.g., 'always assume worst-case fill at bar open').

## P1 (should-fix — fix before implementation)
- **Atomicity Hole in Methodology Disagreement (ADR-0030 D4):** D4 says "Direction disagreement → silence-by-default." However, if a methodology yields a 0 direction (e.g., waiting), does that constitute disagreement with a +1 direction from another methodology, or does the +1 proceed? If a `0` vote creates silence-by-default, a single ultra-conservative methodology will freeze the system. If `0` is ignored, "silence-by-default" is bypassed by adding rules. Propose: Explicitly define how `0` (abstain) interacts with `direction disagreement`.
- **NTA Reconciliation Gap Overnight (ADR-0029 D3, Consequences):** Acknowledges a temporary inconsistency between market close and the 06:00 ET reconcile. If the system stops or crashes and is brought back online *after* 06:00 ET, it misses the reconciliation window entirely. The ledger becomes permanently stale until manual intervention. Propose: Reconcile must not be a naive cron time check. Use a `last_reconcile_asof` watermark. If current time > target, run the reconcile catchup.

## P2 (nits / future work)
- **ADR-0026 D2 (Severity Classification):** The Synthesizer determines severity (`CRITICAL`, `MAJOR`, etc.). This is inherently subjective and prone to LLM drift. It would be safer if severity was defined by objective structural triggers (e.g., "touches a gate threshold" = CRITICAL, "adjusts analyst weight" = MINOR).
- **ADR-0030 D3 (From-reel Pipeline Stage 8 TTL):** The cron job for pulling the latest reels is described as "catching stale extractions". If an influencer deletes a video or changes URL structures, the extraction pipeline will error. Needs specific handling for unavailable source material.
- **ADR-0026 Cost Constraints:** $30/mo is claimed, but the monthly meta-retro (D3) processes 4 weekly reports *and* all proposed amendments for the month. This context window will steadily balloon, potentially blowing past the token limits/budget per run.

## Strengths (what NOT to change)
- **ADR-0026 D4 & D5 (Immutable `evidence_postmortem_ids`):** This is excellent. Tying the amendment explicitly to the trades that caused it creates an auditable chain that prevents theoretical hallucinations from becoming policy.
- **ADR-0029 D6 (Type-level Atomic Proposals):** Prohibiting partial approvals at the schema level rather than just the UI level is a robust defensive programming choice against naked positions.
- **ADR-0030 D1 & D2 (Methodology strictly outputs `AnalystView`):** Forcing external methodology YAMLs to output the same interface the existing PDR committee uses preserves the internal voting and weighting system without muddying the core logic with third-party rules.

## Verdict
ACCEPT-WITH-FIXES. The architectural direction separates human approval from autonomous generation well, but the ability for the retro loop to propose raw codebase diffs (`code_change`) creates an unacceptable risk surface for a money-handling system.
