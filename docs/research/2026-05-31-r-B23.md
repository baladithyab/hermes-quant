# R-B23 — Task-routing decision tree in the system prompt: meaningful for a FIXED deterministic pipeline?

- **Item:** B23 (RESEARCH-THEN-DECIDE). Backlog provenance: "HKUDS G3 — task-routing decision tree in system prompt", capability/P2/S, `docs/research/2026-05-30-backlog-consolidated.md:46`; `docs/architecture/ARCHITECTURE-CRITIQUE-2026-05-27.md:108,205`.
- **Date:** 2026-05-31
- **Verdict: DO_NOT_BUILD.** A prompt-embedded task-routing decision tree is load-bearing only when the LLM *owns the execution path* (dynamic/agentic orchestration over an open tool surface). Hermes-quant's decision pipeline is a fixed, dependency-injected, code-orchestrated workflow with NO LLM-driven path selection. Adding a routing tree to the committee prompts would be cargo-culted from free-form agent frameworks: it adds tokens, prompt-hash churn, and a new (silent) failure mode while changing zero control-flow. The capability it names does not exist in this architecture.

---

## 1. What B23 actually asks for, and where it came from

The gap was lifted from **HKUDS/Vibe-Trading** (the HKUDS repo this project tracks for the "Vibe-Trading" lineage) and cross-listed against TauricResearch/TradingAgents in the 2026-05-27 architecture critique. In both source frameworks the "Task Routing" section is a block of *if/then guidance* inside the LLM system prompt — e.g. "if the user asks for a backtest, load the `strategy-generate` skill then call `backtest`; if they ask for team analysis, call `run_swarm`; ...". B23 proposes porting that idea into hermes-quant's prompt assembly.

The decisive question is whether that block does any work **when the pipeline is fixed**. Answer below.

## 2. Decisive external findings

### 2.1 The reference frameworks route in CODE, not in the prompt (deepwiki, grounded)

- **TauricResearch/TradingAgents** — deepwiki `ask_question`: "the overall routing and sequence of these agents are hardcoded in the LangGraph topology and its conditional edges, not dynamically decided by the LLM through prompt instructions. The system prompts for the LLMs define their roles and tasks within their specific nodes, but not the transitions between nodes." Flow analyst→researcher→trader→risk→PM is fixed by `GraphSetup.setup_graph` + `ConditionalLogic` (`should_continue_*` methods inspecting `tool_calls`/`count`). The prompt has **no routing tree**.
  Source: deepwiki TauricResearch/TradingAgents, https://deepwiki.com/search/does-the-system-prompt-contain_60bac4e6-7f83-446b-b8ba-706cc5070e23

- **HKUDS/Vibe-Trading** — deepwiki `ask_question`: the system prompt DOES contain a "Task Routing" section, **but** "this prompt serves as a guide for the LLM to select appropriate tools and workflows, rather than an explicit if/then decision tree that the LLM directly executes." It is load-bearing *only because Vibe-Trading is a ReAct agent*: `AgentLoop` runs a Thought→Action(tool call)→Observation cycle, and the LLM itself picks which skill/tool/`run_swarm` preset to invoke from a large open surface. The Task-Routing block exists to steer that **open-ended** tool choice; the actual execution is still Python (`SwarmRuntime` DAG, `SwarmTool` keyword-matching presets).
  Source: deepwiki HKUDS/Vibe-Trading, https://deepwiki.com/search/is-there-a-taskrouting-decisio_bb16d63e-145a-4056-9c7c-daef460c2e8a

- **HKUDS/AI-Researcher** — deepwiki `ask_question`: routing is the `MetaChain` orchestrator; tool calls returned by the LLM can carry an `agent` object that becomes the next `active_agent` (LLM-driven handoff). Prompt-embedded tool descriptions guide the LLM's choice, but control flow is Python.
  Source: deepwiki HKUDS/AI-Researcher, https://deepwiki.com/search/does-this-framework-use-a-task_4bb0bbcb-01d0-4c66-9ece-408cfa08922b

**Synthesis:** the routing tree is meaningful **iff the LLM chooses the path**. All three frameworks that "have" it (Vibe-Trading explicitly, the others only as descriptive role text) are agents where the model selects tools at runtime. None of them lets the *prompt* decide transitions in a fixed graph — when the graph is fixed, the transitions live in code.

### 2.2 The workflow-vs-agent literature draws exactly this line

- **Anthropic, "Building Effective AI Agents"** — "*Workflows* are systems where LLMs and tools are orchestrated through predefined code paths. *Agents* are systems where LLMs dynamically direct their own processes and tool usage." Routing (classify → dispatch to a specialist) is listed as a *workflow* pattern; the classification/dispatch can be code or a cheap LLM call, but it is a discrete step, not free-text guidance smuggled into every node's prompt. https://www.anthropic.com/research/building-effective-agents

- **"When Workflow Engines Beat LLM Agents"** (tianpan.co, 2026-04-20) — "If you can draw a complete flowchart of how the process should work … you have a workflow problem." For money/auditability: "An LLM agent running at temperature 0 is still probabilistic … 'The model said so' is not an acceptable audit trail for a financial transaction." Hybrid pattern = deterministic skeleton + LLM as bounded judgment at specific junctions. https://tianpan.co/blog/2026-04-20-workflow-engines-beat-llm-agents

- **Microsoft "Conductor"** (opensource.microsoft.com, 2026-05-14) — "for workflows with known structure … dynamic orchestration adds cost, latency, and unpredictability." Their thesis: "Orchestration should be deterministic and inspectable. Not an LLM making routing decisions." Routing is Jinja2 expression eval; "the orchestration layer consumes zero tokens." https://opensource.microsoft.com/blog/2026/05/14/conductor-deterministic-orchestration-for-multi-agent-ai-workflows/

- **"Agent Orchestration Patterns: Static vs Dynamic"** (agents-squads.com, 2026-01-11) — "The most expensive mistake is over-dynamism: using LLM routing for decisions that don't require intelligence … removing dynamic routing from predictable workflows cut token costs by 25% with no loss in output quality." PR-review checklists and scheduled monitoring pipelines are named as cases where "there's no benefit to an LLM deciding what to check next." https://agents-squads.com/research/agent-orchestration-patterns/

### 2.3 The one contrarian source — and why it does NOT apply here

- arXiv preprint "In-Context Prompting Obsoletes Agent Orchestration for Procedural Tasks" (https://arxiv.org/html/2604.27891v2) argues the *reverse*: for *procedural conversational tasks*, serialize the WHOLE flowchart into the system prompt and let one frontier model self-orchestrate — it beats LangGraph because external per-node injection "fragments reasoning."
  **Why it does not move the verdict for hermes-quant:** (a) its scope is explicitly multi-turn *conversational* procedures (travel booking, tech support, insurance intake) where one model owns the entire dialogue; the authors carve out that "open-ended tasks … may benefit from frameworks" and say nothing about money-handling deterministic pipelines. (b) Its prescription is "put the *whole procedure* in the prompt and let the model run it" — i.e. *move execution INTO the LLM* — which is the polar opposite of hermes-quant's posture (deterministic gate is the final authority, fail-closed, byte-reproducible). Adopting it would mean letting the model own the analyst→aggregator→gate path, which is categorically off the table for money-software. So even the pro-prompt camp does not endorse *a routing tree bolted onto a fixed pipeline* — it endorses *deleting the fixed pipeline*. Neither reading supports B23.

## 3. Repo grounding — hermes-quant is a fixed workflow, not an agent

Read: `hermes_quant/advisor.py` (`recommend`, `recommend_multi_horizon`, `_build_default_analysts`), `hermes_quant/aggregators/llm_committee.py` (full), `hermes_quant/committee_runner.py`.

- **`advisor.recommend()` is a hardcoded pipeline.** Path selection (which analysts, which aggregator, which risk gate) is decided by **code**: recipe → `instantiate_recipe_analysts/aggregator/risk_gate`, else `_build_default_analysts()` whose membership is gated by **env flags** (`HERMES_QUANT_MICROSTRUCTURE`, Kronos, `HERMES_QUANT_FUNDAMENTALS`, `HERMES_QUANT_SEMANTIC_ENABLED`), not by any LLM. Steps are fixed: build `MarketContext` → loop `analyst.analyze(ctx)` → aggregator → risk gate → structured dict. No LLM reads a tree and picks a branch anywhere in this flow.

- **The LLM only appears INSIDE the committee, and even there the route is code.** `run_llm_committee()` (`llm_committee.py:1065`) walks a *fixed* sequence: bull/bear × `max_debate_rounds` → `research_manager` judge → optional risk triumvirate → portfolio_manager. Roles map to templates via a static `_PROMPT_FILES` dict; each role's `system`/`user` text is split from a per-role `.md` (`_split_system_user`). This is literally TradingAgents' LangGraph topology re-expressed as a Python `for` loop with a 2-consecutive-failures bail. The transitions are in code; the prompt carries only that role's task.

- **The prompt surface is per-role and already structured.** `_render_prompt` formats a single role's template with a bounded `fmt` dict. There is no "which role should run next?" decision delegated to the model — `_emit(role)` is called by the loop in a predetermined order. A routing tree would have nothing to route.

- **Posture rails make dynamic routing inadmissible anyway.** `prompt_hash` (SHA-256 over system+user) is journaled for drift detection; failure-closed drops turns; `HERMES_QUANT_RESEARCH_DEBATE` / `HERMES_QUANT_MEMORY_INJECT` are default-OFF and the code is documented as byte-identical when the flag is absent. An LLM choosing the path at runtime would violate determinism (different path per tick), break prompt-hash reproducibility, and put "the model said so" into the audit trail — the exact anti-pattern the money-software posture forbids.

**Conclusion of grounding:** there is no open tool surface and no LLM-owned execution path for a routing tree to govern. The "G3 / task-routing" capability is structurally inapplicable to this codebase.

## 4. Recommended approach for THIS repo

**Build nothing.** Concretely:

1. **Close B23 as DO_NOT_BUILD** in the backlog (`docs/research/2026-05-30-backlog-consolidated.md:46` and the reconciled audit `docs/research/2026-05-31-backlog-audit-reconciled.md`), citing this note. No ADR is required for a no-build, but a one-line ADR-style decision record ("B23 routing-tree: rejected — pipeline is a fixed workflow; routing lives in `advisor.recommend` + `run_llm_committee`, not the prompt") would document the reasoning so it is not re-raised.

2. **Do NOT** add a "Task Routing" section to any file in `hermes_quant/aggregators/prompts/`. Doing so would: (a) change every affected `prompt_hash` (journal/forensics churn for zero behavior change), (b) inject inert if/then text the model cannot act on (it has no tool surface), and (c) risk the model *narrating* a route it isn't taking, confusing operators reading rationales.

3. **If a future need for path-variation appears** (e.g., "use a different analyst loadout for high-vol regimes"), implement it as a **code-level router / recipe selector** in `advisor.py` or the `recipes` module — a deterministic function returning a recipe/loadout — NOT as prompt guidance. That is the Anthropic "routing workflow" pattern done admissibly: a discrete, testable, journaled step. This is a *different* item from B23 and should be raised on its own merits if/when a concrete trigger exists.

4. **Where the real, related value already lives (no new work):** B16 / the other "G3" (markdown render layer over `decisions.jsonl`) is the observability item that IS worth doing and is already tracked separately. Do not conflate the two — they share the "G3" label across two source frameworks but are unrelated capabilities.

## 5. Libraries / APIs

**Stdlib only — and zero net new code.** No dependency, no endpoint, no schema change is recommended. (The existing committee uses the `openai` SDK against an OpenAI-compatible `base_url` per `_build_openai_client`; that is unchanged and irrelevant to this no-build verdict.)

## 6. Pitfalls + rails to respect

- **Cargo-cult risk (the central pitfall):** porting a prompt section because a starred reference repo has it, without checking that the *mechanism* (LLM-owned tool selection) exists here. It does not. Verify mechanism, not surface similarity.
- **Determinism:** an LLM-chosen route would make per-tick paths non-reproducible — violates the byte-reproducibility the journal/`prompt_hash` relies on. Rail: routing stays in code.
- **Silence-contract / fail-closed:** the committee already drops turns on any failure and the deterministic aggregator's BMA fallback covers gaps. A routing tree adds a new failure surface (model picks a wrong/empty branch) with no upside. Rail: do not add admissible-path logic the gate cannot veto.
- **Default-OFF:** even framed as a flag, a default-OFF routing-tree experiment would still incur the audit-churn and inert-text costs in §4.2 with no measurable benefit to gate. Not worth a flag.
- **No-lookahead:** not directly implicated (the change is rejected), but any future code-level router must take `as_of`/`MarketContext` as input and never peek past the bar boundary, same as every analyst.

## 7. Scope decision

**DO_NOT_BUILD.** The capability B23 names (prompt-embedded task-routing decision tree) is meaningful only for free-form agents where the LLM selects the execution path from an open tool surface (confirmed against HKUDS/Vibe-Trading, HKUDS/AI-Researcher, TauricResearch/TradingAgents, and the Anthropic/Microsoft/industry workflow-vs-agent literature). Hermes-quant's decision pipeline is a fixed, code-orchestrated workflow (`advisor.recommend` + `run_llm_committee`), where routing is Python and the LLM is a bounded judgment at fixed junctions — the exact "hybrid: deterministic skeleton + bounded LLM" pattern the literature recommends for auditable/money systems. Adding the routing tree would be cargo-culting that changes no control flow while adding cost, prompt-hash churn, and a silent failure mode, and would conflict with the determinism/fail-closed/auditability posture. No build. The genuinely useful, separately-tracked "G3" item is the `decisions.jsonl` markdown renderer (B16), which is unrelated.
