# R-B29 — Finance Research Goal Ledger (SQLite, status machine, criteria, audit trail) vs the existing JSONL HypothesisRegistry

- **Item:** B29 (RESEARCH-THEN-DECIDE). Backlog provenance: "B1 — Finance Research Goal Ledger (SQLite, status machine, criteria, audit trail)", capability/P2/M, `docs/research/2026-05-30-backlog-consolidated.md:52`; origin `docs/architecture/ARCHITECTURE-CRITIQUE-2026-05-27.md:89` (gap lifted from HKUDS/Vibe-Trading); `gaps.md:107`.
- **Date:** 2026-05-31
- **Verdict: FOLD_INTO_OTHER (fold into B25 / the existing HypothesisRegistry — do NOT build a separate SQLite ledger).** The four capabilities B29 names — *status machine, criteria, audit trail*, and the *durable store* — already exist, shipped, in `hermes_quant/research/hypothesis.py` + `run_card.py`. The only literal delta is the storage engine (SQLite vs append-only JSONL), and that exact choice was **already adjudicated and rejected in ADR-0048 Alt C** ("defeats the portability and simplicity of the append-only JSONL pattern. Rejected for now; deferred to v0.3+ if query patterns demand it"). No query-pattern pressure exists today, and the source ledger's *interactive-agent-session* semantics are inapplicable to hermes-quant's *falsifiable-pre-registration* posture. The residual genuinely-useful deltas (per-criterion satisfied/pending status, `risk_tier` persisted on the row, optional run-linked evidence) are tiny additive fields that belong on the existing JSONL schema under the B25 umbrella, not a parallel database.

---

## 1. What B29 actually asks for, and where it came from

B29 is gap **B1** in the 2026-05-27 architecture critique, lifted verbatim from **HKUDS/Vibe-Trading**'s "Finance Research Goal Ledger". The critique listed it as effort **M**, value 🟢, and grouped it with two siblings that are *also* Vibe-Trading ledger features:
- **B25 / B2** — "Hypothesis Registry richer schema (`monitoring` status, `run_cards[]` linkage)" — **already SHIPPED** (visible in `hypothesis.py` HEAD: the `monitoring` state in `_VALID_TRANSITIONS`, `run_card_ids` field + `link_run_card()`; confirmed DONE Wave 1, `docs/research/2026-05-31-backlog-audit-reconciled.md`).
- **B30 / B3** — "research-only RiskTier keyword guard at goal creation" — **already SHIPPED** (`hermes_quant/research/risk_tier.py`, wired into `HypothesisRegistry.register()`).

So B29 is the *last unbuilt sibling* of a three-item cluster whose other two members are already done by extending the JSONL registry. The decisive question is whether the remaining "SQLite + goal ledger" piece is a real capability gap or a storage-engine cargo-cult. Answer below: it is the latter.

## 2. Decisive external findings

### 2.1 Vibe-Trading's Goal Ledger IS a SQLite store — but it is a *different abstraction* (deepwiki, grounded)

deepwiki `ask_question` on **HKUDS/Vibe-Trading** (two queries):

- **It is an interactive, per-session goal tracker driven by the user/agent during a chat session — NOT a backtest pre-registration mechanism.** "The Finance Research Goal Ledger (`GoalStore`) is an interactive, per-session goal tracker driven by both the user and the agent during a chat session. It is not primarily a pre-registration mechanism for backtests, though backtest results can serve as evidence." Users type `/goal <objective>`, `/goal evidence <index> <text>`, `/goal complete`; the agent calls `start_research_goal`, `add_goal_evidence`, `update_research_goal_status` *as ReAct tools during the loop*.
  Source: https://deepwiki.com/search/is-the-finance-research-goal-l_0a693461-3630-41d4-bed4-36613c4d42bd

- **Criteria are marked satisfied by human/agent AUDIT, not auto-evaluated against metrics.** "Criteria are not automatically evaluated against backtest metrics in a fully automated fashion. Instead, evidence is collected and then audited... To mark a goal as complete, an `AuditRow` is required for every criterion, citing verified `evidence_ids`. This audit can be performed by the user via the CLI or by the agent." This is the polar opposite of hermes-quant's contract, where criteria are eval()'d against the metrics dict by code and the operator cannot retroactively touch them (the entire anti-p-hacking point).

- **Schema (SQLite at `~/.vibe-trading/sessions.db`, class `GoalStore`):** tables `goals` (`GoalRecord`: goal_id, status, objective, risk_tier, budget), `goal_criteria` (`GoalCriterion`: criterion_id, text, status=pending|satisfied), `goal_evidence` (`EvidenceRecord`: evidence_id, text, run_id, artifact_hash, verification_status), `goal_audits` (`AuditRow`: criterion_id, result, evidence_ids), `goal_claims` (`GoalClaim`: thesis|finding).
  Source: https://deepwiki.com/search/does-vibetrading-have-a-resear_b8df161f-bd19-4f65-b07f-8fb934115a3b

- **Its status machine is session/agent-centric, not run-centric:** active · paused · waiting_user · needs_refresh (active); insufficient_evidence · compliance_blocked · budget_limited (blocked); complete · cancelled · superseded (terminal). States like `waiting_user`, `paused`, `superseded` (auto-supersede when a new goal starts in the same session), and `budget_limited` only make sense for a *conversational session controller managing one live objective at a time* — none of them map onto a fleet of falsifiable backtests that run unattended.

**Synthesis:** Vibe-Trading's ledger is the state machine of a chat agent's *current research conversation* (one active goal per session, superseded on a new one, completed by human attestation). Hermes-quant's HypothesisRegistry is a *forensic log of every falsifiable backtest hypothesis ever registered* (many concurrent, auto-adjudicated, never superseded, never human-attested). Porting Vibe-Trading's schema would import an abstraction the system has no use for — and would *weaken* the no-rationalisation guarantee by introducing human "mark satisfied" audit rows where hermes-quant deliberately has machine-only verdicts.

### 2.2 ADR-0048 already decided SQLite-vs-JSONL for THIS exact registry — and rejected SQLite

`docs/adr/ADR-0048-hypothesis-registry-and-run-cards.md` §Alternatives Considered, **Alt C** (verbatim):

> **Alt C: Use a relational database (SQLite).** More powerful querying, but defeats the portability and simplicity of the append-only JSONL pattern. **Rejected for now; deferred to v0.3+ if query patterns demand it.**

And **Alt A** ("Mutate status in-place") was rejected for destroying the audit trail. The append-only-event-replay design (status-change-as-new-row, materialise current state by replay) is the *same contract* as `audit_log.py` (ADR-0031) and `decisions.jsonl` (ADR-0042). B29 is, in substance, a request to re-litigate Alt C. Nothing in the gap text or the external sources demonstrates the "query patterns demand it" trigger the ADR set as the precondition for the SQLite move.

### 2.3 The industry pattern: append-only log is source-of-truth, SQLite is a *derived, rebuildable* read-cache — not a replacement

- **MyPensieve MEMORY-ARCHITECTURE** (decision table N°1): "**Locked choice: Hybrid — JSONL as source-of-truth + SQLite as derived index.** All writes go to append-only JSONL files (the source of truth)... All reads/queries go through SQLite (treat it as a cache)... Backup = the JSONL files; SQLite is disposable... This is the same pattern git uses internally — objects on disk, packed indexes derived." Crucially the SQLite layer is justified only by **cross-project semantic/symbolic query needs at scale**, and is *rebuilt* from JSONL (`mypensieve reindex`). https://github.com/HunterSreeni/MyPensieve/blob/main/docs/architecture/MEMORY-ARCHITECTURE.md

- **arXiv "Audit Trails for Accountability in Large Language Models"** (2026, https://arxiv.org/html/2601.20727) — the reference architecture's Store layer is "append-only, tamper-evident": the PoC `llm-audit-trail` stores a "hash-chained append-only JSONL ledger" with `prev_hash → curr_hash` SHA-256 chaining; "integrity verification reduces to replaying the hash chain, and simple scoped filters are sufficient to reconstruct basic timelines." This is exactly hermes-quant's replay-the-event-log model; SQLite is explicitly *not* required for a tamper-evident research audit trail.

- **weld-cli SPEC_findings** (https://github.com/ametel01/weld-cli/.../SPEC_findings.md) — "Use **SQLite for primary state, JSONL for history logs**": SQLite earns its keep only for *mutable, concurrently-written, frequently-queried* state (chat contexts keyed by id, edited message IDs, "last 5 by status" run history). Append-only history stays JSONL. Hermes-quant's hypotheses are *append-only history*, not mutable state — squarely the JSONL column.

- **MLflow→SQLite case study** (medium, 2026-03) and **SQLiteTracker** (ploomber) — the documented triggers for moving experiment tracking to SQLite are: (a) **concurrent multi-person writes** corrupting file state, (b) **cross-run SQL filtering/sorting** ("best run by metric"), (c) **portability of absolute paths across OS/Docker**. None applies: hermes-quant is single-operator paper-trading, the registry is written under a process-wide `threading.Lock` + `fsync`, queries are whole-file scans of a tiny file, and there are no baked-in absolute paths.

**Synthesis:** the SOTA convergence is *JSONL-as-truth, SQLite-as-optional-derived-cache, adopted only under named query/concurrency pressure*. Replacing the JSONL registry with a SQLite ledger would invert this (mutable DB as source of truth) and is the anti-pattern the audit-trail literature warns against for tamper-evidence.

## 3. Repo grounding — the gap is already closed by the JSONL registry

Read in full: `hermes_quant/research/hypothesis.py`, `run_card.py`, `risk_tier.py`; `hermes_quant/governance/promotion.py`; `docs/adr/ADR-0048`; consumers `hermes_quant/cli/status.py`, `hermes_quant/reporting/daily_report.py`. Import-probed via `~/.hermes/hermes-agent/venv/bin/python3`.

Mapping B29's four named capabilities onto what already ships:

| B29 asks for | Already in the JSONL HypothesisRegistry (verified) |
|---|---|
| **status machine** | `_VALID_TRANSITIONS` (hypothesis.py:96) — `open→running→{monitoring\|validated\|falsified\|abandoned}`, `monitoring→{...}`, `abandoned` from any non-terminal; `_TERMINAL_STATUSES`. `update_status()` enforces it, raising `InvalidStatusTransition`. |
| **criteria** | `success_criteria` / `falsification_criteria` (≤5, ≤256 chars), eval()'d in `{"__builtins__": {}}` scope and **AST-purity-gated** at register time (`_purity_check_criterion` → `factors.ast_purity`). Stronger than Vibe-Trading's free-text criteria. |
| **audit trail** | Append-only JSONL with `kind ∈ {hypothesis, status_change, run_card_link}`, `schema_version=1`, `fsync` on every write, current state materialised by replay; `truncate()`/`update()` raise `AppendOnlyViolation`. Same contract as ADR-0031/0042. |
| **durable store** | `~/.hermes/quant/research/hypotheses.jsonl` + `run_cards.jsonl`; RunCard carries `strategy_config_hash` (SHA-256) for reproducibility, `contamination_guard_fired` to force-falsify lookahead-tainted runs, `artifacts{}` paths (evidence linkage). |
| (SQLite specifically) | **Rejected by ADR-0048 Alt C** until query patterns demand it. They don't. |

Two genuinely-missing-but-tiny deltas vs Vibe-Trading, neither needing a new store:
1. **Per-criterion satisfied/pending status.** hermes-quant evaluates criteria *en bloc* at verdict time (RunCard.`verdict_reasons` already records `[PASSED] sharpe >= 0.5 → True` per criterion). Vibe-Trading tracks each `GoalCriterion.status` independently. If per-criterion state is ever wanted, it is a derived view over `verdict_reasons` — a read-side helper, zero schema/store change.
2. **`risk_tier` on the persisted row.** Already there — `register()` writes `risk_tier` + `risk_tier_flagged` annotations (B30). Vibe-Trading's `risk_tier` column is matched.

**Consumers already depend on plaintext JSONL.** `cli/status.py` reads via `_read_tail_lines` of `hypotheses.jsonl`; `reporting/daily_report.py` diffs `hypotheses.jsonl` over 24h via `_read_hypothesis_changes`. Both `cat`/`grep`/tail the file. Migrating storage to SQLite would force a rewrite of both observability surfaces and break the operator's ability to inspect the trail with shell tools — a regression against the silence-contract/forensics posture, for zero functional gain.

## 4. Recommended approach for THIS repo

**Build no separate ledger. Fold the residual into the existing JSONL registry (B25 umbrella).** Concretely:

1. **Close B29 as FOLD_INTO_OTHER → B25** in the backlog (`2026-05-30-backlog-consolidated.md:52`, reconciled audit), citing this note and ADR-0048 Alt C. Record a one-line decision ("B29 SQLite Goal Ledger: folded into the JSONL HypothesisRegistry; SQLite re-litigation rejected per ADR-0048 Alt C — no query-pattern trigger; Vibe-Trading's session-goal semantics are inapplicable to falsifiable pre-registration") so it is not re-raised. Optionally a thin ADR-0048 *addendum* (not a new ADR) noting the trigger condition for a future derived SQLite index remains unmet.

2. **If, and only if, a real query-pattern need appears later** (e.g. cross-hypothesis analytics like "all falsified hypotheses on AAPL with sharpe<0 in Q1", or the file grows past ~10⁵ rows and tail-scans hurt), implement the MyPensieve/git pattern: a **derived, rebuildable SQLite read-index** built FROM `hypotheses.jsonl` (`stdlib sqlite3`, a `hermes_quant/research/hypothesis_index.py` with a `reindex()` that drops+rebuilds from the JSONL, queries go to the index, JSONL stays source-of-truth, SQLite is disposable). This is a *different, later* item raised on its own concrete trigger — never a replacement of the append-only log. Do NOT do this now; there is no trigger.

3. **The two micro-deltas, if wanted, are additive and JSONL-native** (do under B25, not B29):
   - per-criterion status: a read-side `criteria_status(hyp_id) -> dict[str,Literal["satisfied","failed","pending"]]` helper derived from the latest RunCard's `verdict_reasons` + open/running state. No new write rows.
   - if independent per-criterion *write* tracking is ever needed, add a `kind="criterion_update"` append-only row (same replay pattern as `status_change`) — still JSONL, still ADR-0048-shaped. This is speculative; do not build pre-need.

4. **Do NOT port Vibe-Trading's human-attested `AuditRow`/`goal_audits` model.** It would let a human/agent mark a criterion "satisfied" outside the auto-evaluation path — directly undermining ADR-0048's core guarantee that post-hoc rationalisation is structurally impossible. Hermes-quant verdicts must stay machine-derived from metrics.

The only place SQLite would ever enter is the *deferred, derived* index of §4.2, which would use Python's **stdlib `sqlite3`** (probed: `sqlite_version 3.50.4`, `sqlite3` module 2.6.0 in `~/.hermes/hermes-agent/venv`); pydantic 2.13.3 already present for the models. ## 6. Pitfalls + rails to respect

- **Cargo-cult risk (central pitfall):** porting a SQLite ledger because the source repo (Vibe-Trading) has one, without checking that (a) its *semantics* (interactive session goals, human audit) fit — they don't, and (b) the storage-engine choice wasn't already adjudicated — it was (ADR-0048 Alt C). Verify mechanism + prior decisions, not surface similarity.
- **Audit-trail integrity / append-only:** a mutable SQLite store as source-of-truth *weakens* tamper-evidence vs the replay-the-event-log JSONL design (arXiv 2601.20727 §5.2). Rail: append-only JSONL remains source-of-truth; any SQLite is a disposable derived cache, rebuilt from JSONL, never authoritative.
- **No-rationalisation guarantee (ADR-0048):** do not introduce human/agent "mark criterion satisfied" audit rows. Verdicts stay machine-derived from metrics against criteria frozen at register time. This is the whole point of the registry; Vibe-Trading's audit model violates it.
- **Silence-contract / observability:** `cli/status.py` and `daily_report.py` `cat`/`grep`/tail the JSONL today. A storage migration would silently break these surfaces. Rail: keep the trail shell-inspectable; don't move it behind a DB.
- **Determinism / reproducibility:** RunCard `strategy_config_hash` + `contamination_guard_fired` (force-falsify on lookahead) are the reproducibility anchors and already exist. Any future derived index must be a pure function of the JSONL (deterministic `reindex()`), never a second write path.
- **Default-OFF / fail-closed:** the B30 RiskTier guard (research_only default, opt-in hard-block via `HERMES_QUANT_RESEARCH_RISK_TIER_BLOCK=1`) already implements Vibe-Trading's "prohibit live-trading objectives" rail, fail-closed. Matched; nothing to add. A new ledger would have to re-implement this guard from scratch — another reason not to fork the store.
- **No-lookahead:** not directly implicated (no build). Any future derived view must take the already-recorded rows only and never peek at outcome data unavailable at register time (Oracle Fallacy, ADR-0042/0048).

## 7. Scope decision

**FOLD_INTO_OTHER (→ B25 / the existing JSONL HypothesisRegistry). Do NOT build a separate SQLite ledger.**

Rationale: B29's four named capabilities (status machine, criteria, audit trail, durable store) are all **already shipped** in `hermes_quant/research/hypothesis.py` + `run_card.py` + `risk_tier.py`, with stronger safety than the source (AST-purity-gated machine-evaluated criteria; append-only tamper-evident replay; fail-closed RiskTier guard). The sole literal delta — SQLite vs JSONL — was **explicitly considered and rejected in ADR-0048 Alt C**, deferred to "v0.3+ if query patterns demand it," and no such trigger exists for a single-operator, lock-serialised, tiny-file, no-cross-OS-path registry (the documented MLflow/weld-cli triggers for SQLite all fail to apply). The source ledger's distinguishing features (interactive per-session `/goal`, supersede-on-new-goal, human-attested `AuditRow` completion, `waiting_user`/`budget_limited` states) are *conversational-agent* semantics that are inapplicable to — and in the audit case actively *hostile to* — hermes-quant's falsifiable-pre-registration, machine-adjudicated posture. The industry SOTA (MyPensieve, the arXiv audit-trail reference architecture, weld-cli) is unambiguous that append-only JSONL is the correct source-of-truth and SQLite is at most a disposable derived index adopted only under named query/concurrency pressure. The two genuinely-useful micro-deltas (per-criterion status view; `risk_tier` on the row — the latter already done) are additive read-side helpers / fields on the existing JSONL schema, sized for the B25 envelope, not a parallel database. Building a separate SQLite ledger would duplicate state, fork the RiskTier guard, break the shell-inspectable observability surfaces (`cli/status.py`, `daily_report.py`), weaken tamper-evidence, and risk re-introducing post-hoc rationalisation via human audit rows — all to re-litigate a decision ADR-0048 already made. Fold, don't build.
