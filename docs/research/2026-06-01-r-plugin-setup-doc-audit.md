## 5. The single highest-value gap — the kill-switch recovery hole (H3)

This is the one item to fix first because it is a **one-way emergency stop with no published recovery procedure**, compounded by two same-named mechanisms confusable under stress:

- **Governance kill-switch** — `hermes_quant/governance/kill_switch.py` writes `~/.hermes/quant/state.json`. `clear(token)` calls `approvals.require_human_token('kill_switch_clear','state.json')`, which **only reads pre-existing `grant` rows and NEVER auto-grants** (the module docstring is explicit: "NEVER auto-grants. Including from `--yes`"). `grant_token()` exists but **no CLI verb writes a `kill_switch_clear` grant** (`git grep` over `hermes_quant/cli/*` + `ops/*` = empty), and `grep -rin 'kill_switch_clear|mint' docs/` returns nothing operator-facing. So once fired, the governance halt has **no documented, reachable clear path**.
- **Autonomous auto-trip switch** — `hermes_quant/autonomous.py:231 reset_kill_switch()` simply `unlink`s a **different** file (`~/.hermes/quant/autonomous_kill_switch.json`), exposed as `hermes quant autonomous reset --confirm`. An operator who trips the governance switch and runs `autonomous reset` clears the wrong file and believes the halt is cleared.

The ops docs (GO-LIVE:303, ROLLOUT §5) speak of "the kill-switch" as singular and say clearing "requires a HumanApprovalToken (scope `kill_switch_clear`)… it cannot self-clear" — **without ever telling the operator how to mint that token.** Fix: disambiguate the two switches in the docs, and publish the exact `kill_switch_clear` grant procedure (whatever the intended HITL UX is — a CLI verb that writes a grant row, or the manual `approval_tokens.jsonl` shape) so the emergency stop is reversible.
