# Design Proposal — v0.6.0 R1: Regime in MarketContext.extras

**Status:** Draft
**Author:** subagent (delegated, 2026-05-27)
**Repo HEAD studied:** `1c38ee9` on `main` (note: live tree at `e166d8d` post-merge of v0.5.1 — design unaffected)
**Related ADRs:** ADR-0002 (analyst protocol), ADR-0009 §P1 (extras immutability),
ADR-0036 (multi-horizon fan-out), ADR-0047 (per-regime BMA weight floors),
ADR-0058 (HMM regime classifier v0.2 — label-mapping caveat)
**Companion:** ADR-0063 draft (below, §6)

---

## 1. Problem statement (the gap)

`hermes_quant/protocol.py:80-82` documents `MarketContext.extras` as
"Provider-specific extras (orderbook, news, **regime**, …)". A live audit of the
codebase confirms this is a documentation lie:

* `recommend_multi_horizon` (`advisor.py:539-548`) builds `MarketContext` with
  `extras=dict(market_extras or {})` — whatever the caller supplied, verbatim.
* `tools.py:226` is the only canonical caller and it puts `semantic_packets`
  and `committee_turns` into `market_extras` — never a regime key.
* The HMM regime is computed exclusively *inside* `BMA._aggregate` at
  `aggregators/bma.py:389-395`, **after** every analyst has already returned its
  view. The aggregator uses it for per-regime weight multipliers (ADR-0047)
  and records `regime_state` in `AggregatedSignal.metadata`.

**Net effect:** the four analysts (`ClassicalTA`, `Microstructure`, `Kronos`,
`Semantic`) are blind to regime. A trend-following indicator votes the same
way in a vol-blow-up as in a calm bull tape; a Kronos forecast carries the
same confidence across regime transitions as inside a stable regime; semantic
news weight does not tilt up around event-driven volatility. This is the
single highest-leverage information leak in the v0.5 stack.

R1 fixes this: regime is classified **once**, **before** analyst fan-out, and
flows into `ctx.extras["regime"]` so every analyst (and the aggregator) reads
the same value. Aggregator-side classification is removed in a follow-up
deprecation step (R1.1) but kept temporarily for backward compatibility.

## 2. Where the adapter lives — bars → StateVariables → RegimeState

`HMMClassifier.classify()` takes a `StateVariables` object, not raw bars
(`regime/hmm.py:697`). `compute_state_variables(bars)` already exists in
`regime/state_variables.py`. So the conversion chain is:

```
bars (DataFrame)
  → compute_state_variables(bars)             # regime/state_variables.py
  → StateVariables
  → RegimeDetector.classify(state_vars)       # regime/detector.py:116, returns (RegimeState, reason)
  → (RegimeState, reason_str)
```

**Decision:** option **A** — a dedicated helper module
`hermes_quant/regime/extras_builder.py` exposing `build_regime_extras(bars,
*, asset_class, asof, detector=None) -> dict[str, Any]`.

Rationale (vs option B, classify-in-place inside `recommend_multi_horizon`):

* `advisor.py` is already 960 lines; embedding the bars→regime path inline
  worsens cyclomatic complexity in the highest-traffic file.
* The helper is unit-testable in isolation (`test_extras_builder.py`) without
  needing a yfinance fake or full `recommend()` wiring.
* Phase-3 work (multi-horizon: regime per timeframe) plugs in by calling the
  helper once per horizon — `advisor.py` stays a thin orchestrator.
* The existing pattern in `aggregators/bma.py:389-395` (compute_state →
  detector.classify → record state value) is moved verbatim into this helper,
  giving us a single canonical implementation.

**Module-level skeleton** (informative, not a code mandate):

```python
# hermes_quant/regime/extras_builder.py
def build_regime_extras(
    bars: pd.DataFrame,
    *,
    asset_class: str,
    asof: pd.Timestamp,
    detector: RegimeDetector | None = None,
    min_bars: int = 61,  # _MIN_BARS_FOR_VOL from state_variables
) -> dict[str, Any]:
    """Return the extras subdict to merge into MarketContext.extras.

    Always returns a dict; never raises. Failure modes are encoded in the
    returned dict per §4.
    """
```

`recommend_multi_horizon` calls it once per horizon, *before* the
`MarketContext(...)` constructor, and merges:

```python
regime_extras = build_regime_extras(bars, asset_class=asset_class, asof=last_bar_ts_utc)
ctx_extras = dict(market_extras or {})
ctx_extras.update(regime_extras)   # caller cannot pre-shadow the canonical keys
ctx = MarketContext(..., extras=ctx_extras)
```

Caller-supplied `market_extras` is **shadowed** by the canonical regime keys
(not the other way around) so callers in tests cannot accidentally override
the production regime calculation.

## 3. API contract — what `ctx.extras.get("regime")` returns

After much circling, the design lands on a typed dataclass, **not** a bare
string. The string-only option fails ADR-0058's label-mapping caveat (HMM
state indices ↔ label strings are not stable across retraining); a bare dict
fails type-safety; a top-level enum fails forward-extensibility.

### 3.1 `RegimePacket` dataclass

A new immutable dataclass in `hermes_quant/regime/packet.py` (sibling to
`detector.py`, no circular import risk):

```python
@dataclass(frozen=True)
class RegimePacket:
    label: RegimeState                     # enum, NOT raw string — see §5
    volatility_tier: int                   # -1 | 0 | +1, stable across retraining (see §5)
    posterior: tuple[float, ...] | None    # HMM state probabilities, sum≈1.0; None for rule-based path
    state_vars: StateVariables             # the upstream regime conditioning inputs
    asof: pd.Timestamp                     # UTC; matches MarketContext.asof
    classifier_kind: str                   # "rule_based" | "hmm" | "hmm_synthetic"
    reason: str                            # human-readable diagnostic from detector
```

`extras["regime"]` returns:
* a `RegimePacket` instance when classification succeeded, OR
* `None` when classification failed (see §4).

### 3.2 Why a dataclass, not a dict

* `ctx.extras["regime"].label` is autocomplete-friendly and mypy-checkable.
* `frozen=True` aligns with ADR-0009 §P1 immutability for `extras`.
* Analysts that only need the volatility tier just read
  `regime.volatility_tier` — no string parsing, no dict KeyError surface.
* Forward-compat: adding a `regime_change_score` field later does not break
  consumers that read existing fields.

### 3.3 Auxiliary keys (sibling to `regime`)

To keep the `regime` slot type-pure (`RegimePacket | None`), we put failure
diagnostics in a sibling key:

| `extras` key             | Type                       | When set                                 |
| ------------------------ | -------------------------- | ---------------------------------------- |
| `regime`                 | `RegimePacket \| None`     | Always set (None on failure)             |
| `regime_failure`         | `str \| None`              | Set when `regime is None`; one of §4 codes |
| `regime_classifier_kind` | `str` (`"rule_based"`/etc) | Always set, even on failure (`"unavailable"`) |

Analysts read `ctx.extras.get("regime")` — that's it. The other keys are for
audit logging and the BMA aggregator (which currently already reads
`regime_state` from a different field — it gets refactored to read from this
packet in R1.1).

## 4. Failure-mode handling

The R1 contract explicitly handles four failure modes. **Validation of the
previously-floated `extras={'regime': None, 'regime_failure': '<reason>'}`
proposal: ACCEPTED with the §3 typed-packet refinement.**

| # | Failure                                | `regime`         | `regime_failure`               | `regime_classifier_kind` |
| - | -------------------------------------- | ---------------- | ------------------------------ | ------------------------ |
| 1 | Classifier import fails (module gone)  | `None`           | `"classifier_unavailable"`     | `"unavailable"`          |
| 2 | Insufficient bars (`< 61`)             | `None`           | `"insufficient_bars: n=<N>"`   | `"unavailable"`          |
| 3 | `compute_state_variables` raises       | `None`           | `"state_vars_error: <exc>"`    | `"unavailable"`          |
| 4 | `classify()` raises                    | `None`           | `"classify_error: <exc>"`      | `"hmm"` or `"rule_based"` |
| ✓ | Success (HMM/rule-based both happy)    | `RegimePacket`   | `None`                         | `"hmm"` / `"rule_based"` |
| ◆ | HMM returns `RegimeState.UNKNOWN`      | `RegimePacket`   | `None`                         | `"hmm"`                  |

Important nuance for case ◆: when the classifier *executes successfully* but
returns `UNKNOWN` (e.g., insufficient `realized_vol_percentile` per
`hmm.py:716-717`), we still build a packet with `label=UNKNOWN`. That is *not*
a failure — it is a deliberate hedge from the classifier itself, and analysts
should treat `UNKNOWN` as "do not regime-condition this view". Conflating it
with `regime is None` would discard the diagnostic reason string.

### 4.1 Never-raise invariant

`build_regime_extras` is wrapped in a single `try/except Exception` at the
outermost layer. Any unhandled exception is converted to case 3 or 4 above.
This matches the silence-by-default discipline of `recommend_multi_horizon`
(`advisor.py:438-445`, ADR-0036): a regime failure must never propagate and
prevent the analyst fan-out.

### 4.2 Logging

Every failure path emits exactly one `logger.warning(...)` with the
`asset / timeframe / asof / failure_code` tuple. Successful classifications
log at `DEBUG`. No PII, no DataFrame contents.

## 5. Label-stability — the ADR-0058 caveat

ADR-0058 §"Label mapping stability" warns that HMM state indices `0/1/2/3` are
mapped to `bull/bear/volatile/unknown` post-fit by sorting on heuristics
(mean return × vol). After retraining (or even a different RNG seed) the
*indices may permute*. Downstream code that branches on the literal string
`"bull"` is therefore unstable.

**Hard rule for R1 analyst code:** `regime.label` is for **logging and
human-readable audit only**. Analyst conditioning logic MUST branch on a
*stable, monotone* numeric tier, not on the string label.

### 5.1 `volatility_tier`: the stable tier

Computed inside `build_regime_extras` directly from
`StateVariables.realized_vol_percentile` — bypassing the HMM label entirely:

```python
def _volatility_tier(state_vars: StateVariables) -> int:
    p = state_vars.realized_vol_percentile
    if p is None:
        return 0
    if p < 0.33: return -1   # low vol
    if p > 0.67: return +1   # high vol
    return 0                  # normal
```

This is robust to HMM retraining: the percentile calculation is fully
deterministic given the bars and lookback. A `-1/0/+1` integer is also
trivially serializable and easy to test for invariance.

### 5.2 Why we keep `RegimeState` enum on the packet anyway

* Backward-compat with the existing `regime_state` BMA metadata field
  (callers and dashboards already render the enum value).
* The enum *is* a typed boundary against arbitrary strings — analysts get
  IDE autocomplete and mypy literal narrowing.
* The instability is in the *index→label mapping*, not in the enum
  itself. As long as analysts treat `BULL`/`BEAR`/`VOLATILE`/`UNKNOWN` as
  *categories of an unsupervised classifier*, not as ground-truth regime
  identity, this is safe.

### 5.3 Forbidden patterns

```python
# ❌ FORBIDDEN — anchors on a label string that may flip on retraining
if ctx.extras["regime"].label == RegimeState.BULL:
    boost_trend_signal()

# ✅ ALLOWED — branches on a monotone numeric tier
if ctx.extras["regime"].volatility_tier > 0:
    damp_trend_confidence(0.7)

# ✅ ALLOWED — uses label only for logging
logger.info("analyst running under regime=%s", ctx.extras["regime"].label.value)
```

A custom `ruff` rule (PLR-CUSTOM-001) is added to flag string-literal
comparisons against `RegimePacket.label`. (Configurable; failures are
warnings, not errors, in R1; promoted to errors in R1.2.)

## 6. ADR-0063 draft — Regime in MarketContext.extras

> **File:** `docs/adr/ADR-0063-regime-in-marketcontext-extras.md`
> **Status:** Proposed
> **Date:** 2026-05-27
> **Supersedes:** none
> **Depends on:** ADR-0002, ADR-0009 §P1, ADR-0058

### 6.1 Context

ADR-0058 introduced the HMM regime classifier as an opt-in v0.2 feature wired
into the BMA aggregator. ADR-0047 introduced per-regime weight multipliers,
also consumed inside the aggregator. The original `MarketContext` design
(ADR-0002) already reserved `extras["regime"]` as a documented slot, but no
producer code path ever populated it. As a consequence:

1. Analysts run blind to regime — every analyst sees the same input
   regardless of whether the market is in a calm bull or a volatility
   blow-up.
2. The aggregator computes the regime *after* analyst fan-out, on the same
   bars but redundantly per-call, with no opportunity for the analysts
   themselves to regime-condition their confidence.
3. The doc-vs-reality mismatch is a footgun for new analyst authors who
   read `protocol.py` and assume `extras["regime"]` is populated.

### 6.2 Decision

Regime is classified **once per `(asset, timeframe)` pair, before analyst
fan-out**, by a new helper `hermes_quant.regime.extras_builder.build_regime_extras`,
and surfaced as a typed `RegimePacket | None` at `ctx.extras["regime"]`.

* `recommend()` and `recommend_multi_horizon` call the helper before
  constructing each `MarketContext`.
* The helper is the **single source of truth** for the bars→regime
  conversion. The duplicate path in `aggregators/bma.py:389-411` is removed
  in R1.1 and replaced with `ctx.extras["regime"]` reads (gated behind
  `BMAConfig.regime_source = "context_extras" | "compute_self"` so existing
  callers without the new helper keep working).
* Analyst-side regime usage is governed by §6.5 and the §5 label-stability
  rules.

### 6.3 Consequences

**Positive:**

* Eliminates the largest information asymmetry between analysts and
  aggregator in v0.5.
* Reduces redundant `compute_state_variables` work (currently re-run every
  call inside BMA; now cached per `MarketContext` build).
* Closes the docstring-vs-reality gap in `protocol.py:80`.
* Enables per-analyst regime-conditioning without per-analyst HMM wiring.
* Provides a stable `volatility_tier` channel that survives HMM
  retraining (§5).

**Negative / costs:**

* New mandatory call path in `recommend_multi_horizon` — adds ~5-25 ms per
  horizon (one `compute_state_variables` + one `classify`). Mitigated by
  the silence-by-default never-raise wrapper.
* Backward-compat shim in BMA aggregator until R1.1 (some duplication for
  one minor version).
* New dataclass in the public surface (`RegimePacket`) — must be exported
  from `hermes_quant.regime`.
* Test surface increases by ~6 unit tests (§6.7).

**Neutral / observable:**

* `AggregatedSignal.metadata["regime_state"]` keeps its current string
  format (no breaking dashboard change).
* The `HERMES_QUANT_REGIME_HMM=1` env var still gates HMM-vs-rule choice
  inside `RegimeDetector`; no change there.

### 6.4 Alternatives considered

1. **Bare string at `extras["regime"]`** (`"bull" | "bear" | …`).
   Rejected: violates ADR-0058 label-stability caveat — string literals
   in analyst code become flaky after retraining. Also no posterior or
   `state_vars` audit trail.

2. **Top-level `MarketContext.regime: RegimePacket | None` field.**
   Rejected: every existing analyst signature uses `ctx.extras` for
   provider-specific data; promoting regime to a top-level field forces a
   breaking dataclass change (every test fixture reconstructed) for no
   functional gain over `extras["regime"]`. We can promote in v1.0 once
   the shape is proven.

3. **Each analyst computes its own regime.** Rejected: violates DRY,
   triples HMM compute, and analysts disagree on the regime they're
   conditioning on — defeats the BMA per-regime weight floor invariant
   (ADR-0047).

4. **Lazy/deferred regime: pass a callable in extras.** Rejected: hides
   failure modes from the audit log (caller can't tell if classifier
   actually ran), and analysts are forced into a non-pure-data dependency.

5. **Inline classify in `recommend_multi_horizon` body (option B).**
   Rejected per §2: hurts testability and violates the
   `advisor.py`-as-thin-orchestrator design.

### 6.5 Implementation plan (numbered, executable)

1. **Create `hermes_quant/regime/packet.py`**
   * Define `RegimePacket` `@dataclass(frozen=True)` with the fields in §3.1.
   * Export from `hermes_quant.regime.__init__` alongside `RegimeState`.

2. **Create `hermes_quant/regime/extras_builder.py`**
   * Implement `build_regime_extras(bars, *, asset_class, asof, detector=None, min_bars=61) -> dict[str, Any]`.
   * Internally: bars → `compute_state_variables` → `(detector or RegimeDetector()).classify` → `RegimePacket`.
   * Compute `volatility_tier` per §5.1.
   * Wrap entire body in outer `try/except Exception` per §4.1.
   * Always return a dict with keys `regime`, `regime_failure`,
     `regime_classifier_kind`.

3. **Wire helper into `advisor.py`**
   * In `recommend_multi_horizon`, before `MarketContext(...)`
     construction at line 539, call
     `regime_extras = build_regime_extras(bars, asset_class=asset_class, asof=last_bar_ts_utc)`.
   * Merge: `ctx_extras = {**(market_extras or {}), **regime_extras}` —
     canonical regime keys win.
   * Same change in single-horizon `recommend()` if it constructs
     `MarketContext` independently.

4. **Update `protocol.py:80-82` docstring**
   * Replace the lying claim with a precise statement: "Provider-specific
     extras: `regime` (RegimePacket per ADR-0063), `orderbook`, `news`, …".

5. **Per-analyst opt-in regime usage** (one PR per analyst, behind a
   feature flag `HERMES_QUANT_ANALYSTS_USE_REGIME=1` for the first release):
   * `ClassicalTA`: damp trend-composite confidence by `0.7` when
     `volatility_tier > 0` (chop / vol blow-up). Rationale: trend
     indicators have well-known degraded IC in high-vol regimes
     (Mantshimuli & Mwamba 2026 §3.2).
   * `Microstructure`: boost orderbook-flow confidence by `1.15` when
     `volatility_tier < 0` (low-vol). Rationale: in calm tape,
     order-flow imbalance is a cleaner signal because noise traders
     dominate less; in high-vol, flow is dominated by liquidations and
     becomes noisy.
   * `Semantic` (news/LLM): boost news-driven view confidence by `1.20`
     when `volatility_tier > 0`. Rationale: event-driven volatility is
     where macro news has the highest information content; in calm
     regimes news is mostly noise.
   * `Kronos` (transformer forecaster): damp confidence by `0.85` when
     `regime.label == RegimeState.UNKNOWN` (regime indeterminate / likely
     transition). This is the **one place a label-string check is
     allowed**, because `UNKNOWN` is a fixed, retraining-stable category
     emitted by both the rule-based and HMM classifiers.

   Each adjustment is a small, testable confidence multiplier — no
   structural change to analyst output. All four respect the §5
   forbidden-pattern rule (use `volatility_tier` not arbitrary label
   strings, except Kronos's UNKNOWN check).

6. **Refactor `aggregators/bma.py:389-411`** (R1.1, deferred follow-up)
   * Read `ctx.extras["regime"]` first; fall back to compute-self only
     when regime is None and the new `BMAConfig.regime_source` flag
     allows.
   * Both paths produce identical `regime_state` metadata strings —
     no dashboard break.

### 6.6 Migration

* **External callers of `recommend()`/`recommend_multi_horizon`:** zero
  changes. The helper is invoked transparently. Existing
  `market_extras` keys are preserved (canonical keys merged on top).
* **Analyst implementers:** existing analysts that ignore
  `ctx.extras["regime"]` keep working — no analyst is forced to consume
  the new field.
* **Tests with stub `MarketContext`:** test fixtures that construct
  `MarketContext` directly remain valid; `extras["regime"]` is
  optional.
* **BMA aggregator:** the duplicate compute path stays in v0.6.0 (R1)
  and is removed in v0.6.1 (R1.1) gated by `BMAConfig.regime_source`.

### 6.7 Test plan (≥ 5 unit tests, with invariants)

All tests under `tests/regime/test_extras_builder.py` unless noted.

1. **`test_happy_path_hmm_returns_regime_packet`**
   * Synthesize 252 bars with a clean uptrend.
   * Assert `extras["regime"]` is a `RegimePacket`.
   * Assert `regime.label` is one of `RegimeState` enum values.
   * Assert `regime.volatility_tier in {-1, 0, 1}`.
   * Assert `regime.posterior is None` (rule-based default) OR sums to
     ~1.0 (HMM path with `HERMES_QUANT_REGIME_HMM=1`).
   * Assert `extras["regime_failure"] is None`.

2. **`test_classifier_unavailable_returns_none_packet`**
   * Monkey-patch `build_regime_extras` import surface to simulate
     `ImportError` on `RegimeDetector`.
   * Assert `extras["regime"] is None`.
   * Assert `extras["regime_failure"] == "classifier_unavailable"`.
   * Assert `extras["regime_classifier_kind"] == "unavailable"`.

3. **`test_insufficient_bars_returns_none_packet`**
   * Pass a 30-bar DataFrame (< 61 required).
   * Assert `extras["regime"] is None`.
   * Assert `extras["regime_failure"].startswith("insufficient_bars")`.
   * Assert no exception propagates.

4. **`test_classify_exception_caught_silently`**
   * Inject a detector whose `classify()` raises `RuntimeError("boom")`.
   * Assert `extras["regime"] is None`.
   * Assert `extras["regime_failure"] == "classify_error: boom"`.
   * Assert exactly one `WARNING` log line emitted.

5. **`test_label_string_stability_invariant`**
   * Build a `RegimePacket` with two different fitted HMM seed values
     (using `HMMClassifier(seed=1)` vs `HMMClassifier(seed=2)`) on the
     same bars.
   * Assert `volatility_tier` is identical across the two runs (the
     stable channel).
   * Optionally: assert that whatever `label` value comes back, it
     decodes via `RegimeState(label.value)` — i.e., it is always a
     legal enum member and never a free-form string.

6. **`test_unknown_label_is_not_a_failure`** (extra, for the §4 ◆ case)
   * Pass bars that lead to `RegimeState.UNKNOWN` but a successful
     classify (e.g., just-barely-enough bars for vol but no trend).
   * Assert `extras["regime"]` is a `RegimePacket` with
     `label == RegimeState.UNKNOWN`.
   * Assert `extras["regime_failure"] is None`.

7. **`test_caller_extras_cannot_shadow_regime_keys`**
   * Call `recommend_multi_horizon(..., market_extras={"regime": "evil"})`.
   * Assert the resulting `ctx.extras["regime"]` is the canonical
     `RegimePacket | None`, not `"evil"`.

**Integration test** (one, in `tests/integration/test_advisor_regime_flow.py`):

8. **`test_advisor_recommend_propagates_regime_to_analysts`**
   * Use a fake analyst that records `ctx.extras.get("regime")` on
     every `analyze()` call.
   * Run `recommend_multi_horizon("AAPL", horizons=("1d", "1w"))`.
   * Assert each recorded `extras["regime"]` is non-None for both
     horizons, OR if None, the corresponding `regime_failure` is set.
   * Assert that across horizons, `volatility_tier` is in
     `{-1, 0, 1}`.

### 6.8 Out of scope for R1

* Per-asset regime priors (different volatility tiers for crypto vs
  equity). v0.6.2.
* Cross-horizon regime consistency check (warn when 1d and 1w disagree
  by more than one tier). v0.6.2.
* Regime-transition score (probability that we're between two states
  rather than firmly in one). v0.7 — needs HMM smoothed posteriors.
* Promoting `regime` from `extras["regime"]` to a top-level
  `MarketContext.regime` field. v1.0.

## 7. Summary of design decisions (for reviewers)

| # | Question                              | Answer                                                              |
| - | ------------------------------------- | ------------------------------------------------------------------- |
| 1 | Where does bars→regime live?          | `regime/extras_builder.py` (option A)                                |
| 2 | Type of `extras["regime"]`?           | `RegimePacket \| None` (frozen dataclass, not a bare string)        |
| 3 | Failure-mode shape?                   | `regime=None` + sibling `regime_failure` code + `regime_classifier_kind` |
| 4 | Label-string anchoring?               | Forbidden in analyst conditioning; use `volatility_tier ∈ {-1,0,1}` |
| 5 | Per-analyst usage?                    | One concrete confidence multiplier each (§6.5 step 5)               |
| 6 | Aggregator duplicate path?            | Kept in R1, removed in R1.1 behind `BMAConfig.regime_source`        |
| 7 | Caller extras override regime?        | No — canonical keys merged on top                                   |
| 8 | Never-raise?                          | Yes — outer `try/except` per §4.1, matches ADR-0036 silence rule    |

## 8. Open questions for human review (do not auto-resolve)

* **Q1:** Should the per-analyst confidence multipliers (§6.5 step 5) be
  hardcoded in each analyst, or live in a shared `analysts/regime_adjustments.py`
  table for easier tuning? Recommendation: **table**, mirroring the
  per-regime BMA weights pattern in `regime/per_regime_weights.py`.
* **Q2:** Should the feature flag `HERMES_QUANT_ANALYSTS_USE_REGIME` default
  to `1` (on) at v0.6.0 release, or default to `0` for one minor release to
  collect IC deltas? Recommendation: **default off in v0.6.0, on in v0.6.1**
  after one cycle of telemetry.
* **Q3:** Posterior probabilities — `HMMClassifier.classify()` currently
  returns only the argmax state. Should we extend it to return the full
  posterior tuple for the packet, or leave `posterior=None` until v0.7?
  Recommendation: **leave None in R1**; ship the channel, fill it later.
