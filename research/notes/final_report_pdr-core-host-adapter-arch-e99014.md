# Best-Possible Architecture for a Money-Software Trading System: One Host-Agnostic Deterministic Core, N Agent-Host Adapters

**The verdict up front: extract the shared core. ADR-0092's Option D is correct, and the strongest argument against it — that shared internal libraries become "shared shackles" — actually concedes the case once you recognize what kind of artifact a money-core is.** Every mature multi-venue trading system surveyed (nautilus_trader, Lean, vn.py, hummingbot) factors heterogeneous producers from a shared decision core through exactly the seam ADR-0092 proposes: an abstract adapter contract plus a canonical, normalized domain model. The 2025-2026 empirical record on LLM trading agents is even more one-sided: it converges, hard, on the charter's two load-bearing rails — the deterministic gate as final authority, and no-look-ahead. ADR-0092 is right on its big decisions. It is under-specified on five concrete mechanisms, and on one of them (monorepo versus published-and-pinned) it punts entirely. This report names all five.

The factoring is not exotic. It is the dominant pattern in the field, and the failure mode it prevents — heterogeneous adapters each re-deriving and re-breaking the money-bearing state — is a documented, recurrent disease with a known cure. hermes-quant's confirmed defects (dual-ledger divergence, two-of-four fire-paths bypassing the cap, fixture-leaked fictional P&L) are textbook instances of that disease. The interesting questions are not *whether* to extract a core but *how precisely* to draw four seams: the contract triad, the money-state model, the gate's polarity enforcement, and the contract-evolution mechanism. Those are where this report spends its evidence.

## 1. The Core/Adapter Boundary: Contract-Seam Design and How Mature Trading Systems Factor It

### The proven seam is an abstract adapter contract plus a canonical normalized domain model

Across four independently-built, production-grade trading systems, the core/adapter factoring is the same shape. Each defines an **abstract adapter contract** and a **canonical normalized domain model** that adapters translate venue-native data into and out of. The core never touches a venue API; adapters never touch core decision logic.

- **nautilus_trader** is explicitly "ports and adapters": adapters translate native venue APIs into a unified internal domain model (instrument types, `QuoteTick`, order commands, execution events) ([[nautilus_trader-ports-and-adapters-venue-integration]]). The core uses a fixed-point precision system for prices, quantities, and money specifically to avoid floating-point error — a money-correctness practice worth lifting wholesale.
- **Lean (QuantConnect)** is interface-driven: `IBrokerage` is the contract all brokerages implement; the canonical model is the `Order` class; per-venue idiosyncrasy lives in `IBrokerageModel.CanSubmitOrder()` — *inside the adapter*, not the core; and `BrokerageTransactionHandler` is the intermediary that keeps portfolio/risk logic decoupled from any brokerage's implementation ([[quantconnect-lean-interface-driven-brokerage-adapters]]). Lean answers the precise question "what does the adapter own versus the core" cleanly: the core owns the canonical contract and the transaction handler; the adapter owns venue rules.
- **vn.py** uses `BaseGateway` (connect/subscribe/send_order/cancel_order/query) plus canonical `BaseData` objects (`OrderData`, `TradeData`, `PositionData`, `AccountData`), with gateways publishing to a pub/sub `EventEngine` ([[vnpy-basegateway-eventengine-canonical-object-seam]]).
- **hummingbot** layers `ConnectorBase` → `ExchangeBase` → `ExchangePyBase`, with an `InFlightOrder` state machine and a `ClientOrderTracker` ([[hummingbot-connector-standardization-what-early-connectors-got-wrong]]).

ADR-0092's `AnalystView`-as-seam is the identical move, lifted one layer up the pipeline. Where these systems normalize *venue execution data*, ADR-0092 normalizes *perception*: the contract that makes the aggregator blind to which analyst produced a view is the same contract that makes the core blind to which host produced it. This is the natural factoring, not a forced one — and it is rare in a good way. As Martin Fowler notes, a strangler-fig migration depends on finding **seams** to split the system, and "in a well-designed system these seams would already exist. But such systems are unicorns" ([[strangler-fig-gradual-replacement-transitional-architecture-seams]]). hermes-quant already has its seam. That is a substantial, underappreciated asset, and it is the reason a gradual extraction (Option D) dominates a from-scratch rewrite (Option A): the rewrite discards the one thing — a working, host-blind contract plus ~74K LOC of clean leaves — that makes the strangler approach low-risk.

### What they got wrong first — and why it is hermes-quant's exact disease

The most valuable evidence comes from hummingbot's *history*. Early hummingbot connectors each re-implemented their own order tracking, API throttling, and time synchronization. The results were duplicated logic, inconsistent error handling, "lost orders" that vanished from venue responses with no dedicated tracker to re-query them, and ad-hoc per-connector rate-limiting that triggered API bans ([[hummingbot-connector-standardization-what-early-connectors-got-wrong]]). The fix was to **pull the state machinery up out of the per-adapter code into a shared base** — `ClientOrderTracker`, `WebAssistantsFactory`, `AsyncThrottler`, `TimeSynchronizer`.

That is hermes-quant's situation stated in another project's words. When adapters each own a slice of money-bearing state, you get divergence (hermes' dual-ledger), inconsistent rails (hermes' two-of-four cap-bypass), and lost-state bugs. The remedy hummingbot converged on — centralize the state machine, thin the adapters — *is* ADR-0092's prescription. This is not a theoretical analogy; it is a second team independently arriving at "the core owns the state machinery; adapters only translate," after the alternative bit them.

There is also a cautionary contrast inside the survey. vn.py wires its risk module as an **event subscriber** to the `EventEngine`, not as an inline chokepoint on the order path ([[vnpy-basegateway-eventengine-canonical-object-seam]]). nautilus_trader, by contrast, places the `RiskEngine` **synchronously before** the `ExecutionEngine` on every path: a strategy's order passes through pre-trade risk *before* routing to any adapter ([[nautilus_trader-ports-and-adapters-venue-integration]]). The difference is decisive for money-software. An async risk-subscriber can lag, miss a path, or race — which is precisely how a cap gets bypassed. hermes-quant's confirmed "two-of-four fire-paths bypass the cap seam" defect is the vn.py topology failing in the wild. **ADR-0092's insistence on a single synchronous `execute()` chokepoint with one gate node on every path is the nautilus topology, and it is the correct one.** A control wired once at a synchronous chokepoint is inherited by every caller by construction; a control that listens for events is only as reliable as the weakest emitter.

### The boundary-leak failure mode, named

When a ports-and-adapters boundary "leaks," the failure is specific: a port is defined at the **wrong level of abstraction**, exposing *how* the infrastructure works rather than *what* the domain needs. A leaky `OrderRepository.executeQuery(String sql)` tells the domain it sits on a relational database; a `PaymentGateway.post(url, headers, json)` leaks HTTP; a port returning a DynamoDB `AttributeValue` leaks the datastore. "Your domain is shaped by your infrastructure... that's the opposite of decoupling" ([[hexagonal-driven-ports-leaking-infrastructure]]). The diagnostic question is: *does this interface expose what the domain needs, or how the infrastructure works?*

This is the live hazard for `AnalystView`. The contract must express what the decision core needs — a peer view with a direction, a confidence, a publication-time `asof`, and evidence references — in domain language. The moment it carries an MCP tool-call shape, a Claude-subagent message struct, a cron-tick timestamp, or a Python analyst class's internals, the core is coupled to a host and the "host-blind seam" claim quietly fails. The operational test is concrete: **could you add a third agent host without touching the core's contracts?** If any field answers "how did this host produce it," the port leaks. ADR-0092 is right that `AnalystView` is the seam; it is silent on the discipline that keeps the port at domain abstraction. That discipline should be named as an explicit invariant — *no host or infrastructure types appear in any core contract* — and enforced with a fitness test, not left to reviewer vigilance.

## 2. The Money-State Model: Append-Only Ledger vs Materialized State

### The dual-ledger bug has a name, and event sourcing is the named cure

hermes-quant's dual-ledger divergence — two reconstructors reading the same `executions.jsonl` with incompatible semantics, so that re-affirming +0.20 twice yields 0.40 in one book and 0.20 in the other — is a special case of the **dual-write problem**: the inconsistency that arises whenever two stores (or two readers of one store with two interpretations) must agree but are updated or interpreted independently. The canonical analysis is unambiguous about what does *not* fix it: reordering the writes just moves the inconsistency; a database transaction does not extend to a second store; in-memory retries die on crash; durable retries reintroduce a second write ([[dual-write-problem-and-event-sourcing-as-the-cure]]).

The cure is to make **one write authoritative and derive everything else from it.** Event sourcing does exactly this: "the event is written to a single row in a single table. A transaction is unnecessary... When the application needs state, it reads the events back and uses them to rebuild it." The same source observes that "this model works well for banking because accounts are *naturally* event-sourced. Banks keep a full history of every deposit and withdrawal." ADR-0092's single `Ledger.portfolio()` fold, read identically by every consumer, *is* this cure. The dual-ledger class becomes structurally impossible because there is one log of intent and one fold; projection and settlement-FIFO consumers derive from the same fold rather than re-deriving truth independently.

TigerBeetle, a purpose-built financial ledger, reinforces every adjacent choice. Double-entry debit/credit is "minimal and complete: two entities (accounts, transfers) and one invariant (every debit has an equal and opposite credit) model any exchange of value." Immutability is non-negotiable: "once transfers are recorded, they cannot be erased. Reversals are implemented with separate transfers to provide a full and auditable log" ([[tigerbeetle-debit-credit-immutability-in-ledger-invariants]]). And accounting invariants such as balance limits are enforced *within* the ledger, "avoiding round-trips between database and application logic." The history is its own argument: Uber (a two-year, forty-engineer migration), Airbnb, and Stripe all started with roll-your-own transaction systems and converged on double-entry plus an immutable event log. "Don't roll your own ledger."

This yields a concrete improvement to name. ADR-0092's core owns "all money-adjacent state + arithmetic + the gate." TigerBeetle suggests the ledger's *shape*: consider modeling it as **double-entry** (a cash account and per-instrument position accounts) rather than a flat position log, so that "money never appears from nowhere or disappears" becomes a structural invariant the fold can assert on every read, not a property hoped for. nautilus_trader's fixed-point money type is the complementary, lower-cost adoption: integer or decimal money, never floats.

### Reconstruct vs materialize — and the trap that re-opens divergence

The tension here is real and worth engaging head-on rather than waving away. A pure single-fold-reconstruct-on-every-read is always correct but pays a recomputation cost per read; a materialized state store is fast but is *exactly* the second store whose independent maintenance caused the divergence in the first place. The CQRS discipline resolves it without surrendering correctness: **the fold defines truth; a materialized projection is permitted only as a derived cache that is provably rebuildable from the log and is asserted byte-identical to the fold by a property test.** Never a second writer; never a second interpretation. The projection is an index over the log, not a competing record.

The sequencing matters for a money system mid-migration: hermes-quant's bug was divergence, not latency. The right default is to ship the single fold as the only source of truth, leave any materialized projection default-OFF behind the `projection == fold` property test, and turn it on only when a measured read-latency problem justifies it. Optimizing first would re-arm the exact failure the rearchitecture exists to kill.

This section also adjudicates the open ADR-0091 fork, because the money-state model and the contract-evolution model are the same decision viewed twice. ADR-0091's option B (producer emits a delta computed from derived state) requires a writer to read derived state in order to write the immutable log — a write-time coupling into an append-only store, which the dual-write analysis identifies as precisely the kind of dependency that creates inconsistency. ADR-0091's own durable lesson states it: "a fix that requires a producer to read derived state to compute a value is a write-time race into an immutable log — strictly worse than a read-time projection bug." Option C (version-discriminated carry-forward fold) interprets older records at *read* time and keeps the log a pure record of intent. Section 4 shows that option C is textbook event-sourcing practice. The money-state evidence and the contract-evolution evidence point the same direction: **keep the log a pure, immutable record of intent; resolve all version and semantic differences at read time.**

## 3. Deterministic Gate as Final Authority: Evidence-Only LLMs and Monotonic Authority

### Monotonic-forward authority is a recognized, formalized pattern: it is a shield

The charter's rule — the LLM committee "may silence via a 0.0 multiplier, never amplify or re-select" — is not a bespoke invention. It is the **shielding** pattern from safe reinforcement learning, and it comes with formal guarantees. A shield is "a mechanism that provides formal safety guarantees by preventing unsafe actions from being executed at runtime... while restricting the agent as little as possible" ([[safe-rl-shielding-formal-monotonic-restriction-prior-art]]). Two variants map directly onto a trading gate. In **post-shielding**, the shield sits between agent and environment and replaces an unsafe action with a safe one. In **pre-shielding**, the shield provides the *list of safe actions* and the agent picks from it. Either way, the shield can only *remove* options from the agent's choice set — never add. That is monotonicity, stated structurally.

Two further results from this literature are load-bearing for the design. First, **separation of concerns**: "the features used in the safety constraint need not be the same as those used by the learning agent," and an agent trained under such masking "can still learn any optimal policy that satisfies the safety constraints." Restriction costs nothing in reachable-optimum terms, and the safety layer is entitled to use its *own* deterministic state rather than trusting the agent's self-report. Applied here: the gate computes risk from its own ledger-derived state, not from numbers the LLM hands it. Second, the **break case** is explicit: "the shield is unable to provide a safe action if no safe action exists. In such cases the practical solution is to lower the safety requirements, if possible." For a trading gate, this is where silence-by-default earns its keep — an empty admissible set is not a crisis requiring a relaxed cap; it is simply *do nothing*. The shield's other failure mode is subtler and must be designed against: a shield only guarantees safety with respect to the abstraction it watches, so an incomplete shield, or one watching the wrong state, yields **false safety**. The mitigation is the single synchronous chokepoint of Section 1 — the gate must be on *every* path, or it is not complete.

### Structural, not prompt-level, enforcement — and the trap to avoid

The field offers a clean three-way contrast on how to enforce gate polarity, and the differences are the whole ballgame.

- **TradingAgents** (TauricResearch) is the **anti-pattern exemplar**. Its analyst team, bull/bear debate, and aggressive/conservative/neutral "risk management team" all feed a **Portfolio Manager that is the final authority** — an LLM emitting a structured rating, with a free-text fallback in the loop ([[tradingagents-llm-as-final-authority-anti-pattern]]). The "risk team" only debates; nothing deterministically vetoes. This is exactly what the charter forbids, in the most-cited multi-agent trading framework. Popularity is not correctness.
- **ai-hedge-fund** (virattt) is **most of the way right**. Its risk manager is *deterministic* — it computes position limits in pure Python from volatility and correlation — and `compute_allowed_actions` deterministically bounds the choice set before the LLM acts ([[ai-hedge-fund-deterministic-risk-gate-constrains-llm]]). But the final step instructs the LLM to "pick one allowed action per ticker and a quantity ≤ the max." The constraint is computed structurally yet *delivered as a prompt*. A misbehaving model can emit a quantity above the max; whether code clamps it afterward is the open question. This is the residual leak to design out.
- **Vibe-Trading** (HKUDS) is the **closest external analog to the charter** and shows the correct enforcement. Its `LiveOrderGuardTool` is a **fail-closed** deterministic gate, separate from the LLM, enforcing a versioned Mandate with HardCaps on order notional, total exposure, leverage, and trades-per-day, an instrument whitelist, a kill-switch halt flag, and `pause-for-reauthorization` with a `BreachEvent` on violation. "The LLM proposes sizing and direction; the `LiveOrderGuardTool` validates and enforces against pre-configured limits regardless of the LLM's recommendation" ([[vibe-trading-liveorderguardtool-fail-closed-deterministic-gate]]). The LLM's recommendation is overridden by the gate. This is "evidence, not authority," realized in a 2025 production-shaped system.

The synthesis prescribes a specific structural form that closes ai-hedge-fund's leak. The core computes the sized envelope — a deterministic maximum — from its own ledger-derived risk state. The committee emits only a confidence in `[0,1]` (or silence). The core computes:

> `size = deterministic_max × clamp(committee_multiplier, 0, 1)`

The LLM never names a size and never sees the maximum. A `0.0` multiplier is silence; any value in `(0,1]` can only scale the deterministic maximum *down*. **Amplification is structurally impossible because the model's only output is a bounded multiplier on a number it cannot set.** This is a pre-shield expressed in one line of arithmetic, and it is the difference between a polarity that holds because the prompt asked nicely and one that holds because the type system and the multiplication make the violation unrepresentable. ADR-0092 states the polarity correctly but does not pin the enforcement mechanism; this is the under-specification to fix.

### Why the empirical record makes this posture mandatory, not merely cautious

It would be tempting to read "deterministic gate as final authority" as conservatism. The 2025-2026 evidence says it is the only defensible posture. Under leakage-free *live* evaluation — trading only on data published after each model's pretraining cutoff — "even cutting-edge models such as DeepSeek-V3 and Claude-3.7-Sonnet incur net trading losses" ([[deepfund-time-travel-is-cheating-leakage-free-live-eval]]). The base rate for frontier-LLM autonomous trading, evaluated honestly, is *negative*. A system that lets the model be the final authority is betting on a capability the field has not demonstrated. A system that demotes the model to evidence — silence-only, never amplify — loses nothing the model could reliably provide and forecloses the documented downside.

## 4. Contract Evolution Across Independently-Deployed Plugins

### Never mutate the log; upcast at read time — which is exactly ADR-0091's option C

Event-sourcing practice has a settled answer to versioning a shared, append-only log consumed by code on different release cadences, and it aligns precisely with the money-state conclusion of Section 2. The first rule is **never change the past**: "having precise information, even including bugs, is a valid scenario" ([[event-schema-versioning-upcasting-vs-copy-replace-never-mutate]]). Compatible changes (new optional fields, new required fields with defaults, renames via serialization mapping) are handled at the schema level. Genuinely structural changes use **upcasting** — "middleware between deserialization and application logic" that reads an old event and transforms it to the new shape *at read time*. Old records stay on disk in their original form; the reader produces the current shape.

Upcasting *is* a version-discriminated carry-forward fold. ADR-0091's option C is therefore not a novel risk; it is the canonical, low-risk event-sourcing practice, and it is **interpretation at read time, not mutation of the log** — the opposite pole from option B's write-time coupling. The heavyweight alternative, copy-and-replace (rewrite the stream into a clean log), is reserved for when a pristine log is pragmatically required and is explicitly the exception, not the default. For two plugins on different cadences, the mechanism is clean: the shared core ships an **upcaster registry** as part of its versioned contract; each shell's pinned core version knows how to interpret older log records forward; no shell ever rewrites the shared log. Keeping event streams short-lived (so old-schema instances age out within a deploy window) makes even this nearly free.

### Monorepo-with-path-dependency, not separately-published-and-pinned

This is the one decision ADR-0092 leaves genuinely open, and it deserves a committed answer because it is where the most credible objection to the entire proposal lives.

The objection, stated at full strength: shared internal libraries are "shared shackles." They couple independently-deployable components, force version-conflict and upgrade pain ("one place to maintain becomes one place that blocks everyone"), turn two-hour changes into two-week dependency chains, and obscure accountability — and "a shared library is almost never the right answer because the problem it solves (duplicated code) rarely justifies the problems it creates" ([[shared-libraries-become-shared-shackles-adversarial]]). ADR-0092 itself lists "a third versioned artifact... coordination cost on every contract change" as a required negative. The objection must be answered, not dismissed.

It answers itself. The same source carves out a single exception where a shared library is right: **security protocols** — when "the domain is stable and well-understood," "the cost of getting it wrong is catastrophic," "the surface area is thin and focused," and "autonomy isn't the goal — you actually want teams to do it the same way; the coupling is a feature, not a bug." A money-core matches that profile on all four counts. Double-entry accounting is centuries old (stable). A defect debits a real bank account (catastrophic). The core is ledger plus gate plus typed contracts plus fold (thin and focused). And you *want* both hosts to do money identically — divergence is the bug ADR-0092 exists to kill, so coupling is the point. The money-core is the conceded exception, not the warned-against utility wrapper. The objection's force should nonetheless be heeded as a boundary on scope: **keep the core minimal.** It must not accrete host helpers, "convenient" perception utilities, or API-client cruft, or it slides from the security-protocol exception into the shared-shackle anti-pattern. Host-specific perception and reaction stay in the shells.

On the packaging mechanism specifically: the "shared shackle" costs — version conflicts, cross-team blocking, coordination chains — are overwhelmingly *multi-team, multi-repo* costs. hermes-quant and cowork-quant share one operator. The monorepo's signature advantage is **atomic cross-cutting change**: when the contract changes, a single commit updates the core and both shells together — exactly the operation you perform most when a money-contract evolves. A separately-published-and-pinned package, by contrast, *imposes* the coordinated two-shell migration ADR-0092 fears; that coordination cost is a polyrepo cost you can simply decline to incur. **Recommendation: a monorepo with the core as a path-dependency, each shell pinning a core version for reproducibility and rollback, breaking changes landed atomically across all three.** This preserves per-shell reproducibility without paying the cross-repo coordination tax. Revisit only if a second author or organization takes ownership of one shell — at which point the calculus genuinely shifts toward a published, semver-pinned package (the `semver-trick` exists precisely to ship breaking changes to such a shared core without a lockstep migration).

## 5. Multi-Agent Trading Architecture SOTA and Documented Anti-Patterns

### What the leading systems actually do for perception → decision → reaction

The three reference systems span the full spectrum of gate polarity, which is what makes them instructive together.

- **TradingAgents** splits perception (fundamentals/market/news/sentiment analysts) → decision (bull/bear debate → research manager → trader) → a risk-management debate → a Portfolio Manager. Signal unification is *dialectic*: agents argue, a manager synthesizes. The analysis/risk separation is nominal — the "risk team" is another debate, and the LLM Portfolio Manager holds final authority ([[tradingagents-llm-as-final-authority-anti-pattern]]).
- **ai-hedge-fund** splits perception (per-persona analyst agents emitting signal + confidence + reasoning) → a **deterministic** risk manager computing position limits → a portfolio manager that picks within a deterministically-computed allowed-action set ([[ai-hedge-fund-deterministic-risk-gate-constrains-llm]]). Signal unification feeds named analyst signals into a deterministic envelope. The analysis/risk separation is *real*: risk is code, not an LLM.
- **Vibe-Trading** splits perception (funding/liquidation/flow analysts in a DAG "swarm") → decision (a strategist/manager synthesizing an executable plan) → execution **guarded by a separate deterministic risk-control module** (`LiveOrderGuardTool`) ([[vibe-trading-liveorderguardtool-fail-closed-deterministic-gate]]). The analysis/risk separation is architectural and fail-closed.

The charter's PDR model — perception producing `AnalystView`s, a deterministic decision core, a deterministic gate before reaction — is the ai-hedge-fund/Vibe-Trading lineage with the gate polarity made structural and explicit. It is on the right side of the only axis that the empirical record can adjudicate.

### What has been shown not to work

**LLM as final execution authority.** Under honest, leakage-free live evaluation, frontier models lose money ([[deepfund-time-travel-is-cheating-leakage-free-live-eval]]). A system that makes the model the final authority inherits that negative base rate. TradingAgents is the cautionary exemplar precisely because it is respected and widely copied.

**Backtest-validated LLM alpha (the look-ahead trap).** "Most systems exhibit a 'profit mirage': dazzling back-tested returns evaporate once the model's knowledge window ends, because of the inherent information leakage in LLMs" ([[profit-mirage-llm-financial-agent-information-leakage]]). The leakage is measurable: on a memorization probe ("did the market rise on date T?"), GPT-4o and peers answer correctly over 85% of the time — the facts are memorized — and across a historical-versus-recent comparison with near-identical market returns (+13.79% vs +13.35%), agents suffer a **55.68% Sharpe decay** out-of-window. "LLM-based agents are not genuinely forecasting but rather recognizing patterns from their training data." This is the quantitative justification for the charter's no-look-ahead rail: `asof` = publication time is not hygiene, it is the difference between a real signal and a memorized one. The corrective the paper itself reaches for is telling — demote the LLM "to a strategy generator rather than a direct decision-maker." That is the charter's evidence-not-authority polarity, arrived at independently.

**Free-text position sizing.** The fix demonstrated by ai-hedge-fund and Vibe-Trading is to compute the size deterministically and let the model choose only *within* a computed envelope (and, per Section 3, only as a downward multiplier it cannot exceed). Free-text sizing hands an unbounded number to a component with a negative live base rate.

**RL-on-portfolio-value.** Reward-on-book-value RL "learns the offline policy — transactions that yield the highest profits within the dataset — even though such a policy may not be generalizable outside the dataset's scope," because "offline policies fail to account for the non-stationary nature of the market" ([[rl-on-portfolio-value-fragility-offline-policy-not-trustworthy]]). It is the RL analog of the profit mirage: an in-sample maximum that does not survive distribution shift. This validates confining learning to eval-gated, out-of-sample-validated, default-OFF components rather than an end-to-end agent optimizing book value.

The through-line across all four: the field's documented failures are failures of *authority misplacement* and *evaluation dishonesty*. The charter's rails — deterministic gate as final authority, no-look-ahead, default-OFF behind eval gates — are not conservatism. They are the precise set of constraints the 2025-2026 literature independently recommends.

## 6. Verdict on ADR-0092: Confirm, Under-Specified, and Contradicted

**Where ADR-0092 is right.** Option D over the alternatives: the survey and the strangler-fig literature confirm that gradual extraction across an existing seam dominates a from-scratch rewrite, and the hummingbot history confirms that centralizing money-state is the proven cure for adapter-level divergence. `AnalystView` as a host-blind, modality-blind seam is the same factoring every mature trading system uses, one layer up. The core owning all money-state, arithmetic, the gate, and the typed contracts is the security-protocol exception that even the sharpest anti-shared-library argument concedes. Keeping the auto-execute-versus-route-to-human decision in the shell, invisible to the core, is directly supported: the AgentOS `ApprovalRequest → handler → ApprovalDecision` contract shows one gate serving both an auto-approve handler and a human-routed handler, with non-2xx treated as rejection (fail-closed) ([[hitl-approvalrequest-handler-approvaldecision-fail-closed]]). Consuming whatever ADR-0091 resolves to, rather than pre-empting it, is correct — and Sections 2 and 4 independently point that resolution toward option C.

**Where ADR-0092 is under-specified (five named fixes).**

1. **The seam is a triad, not a single contract.** ADR-0092 names `AnalystView` as "the seam" but the survey shows a complete factoring needs canonical contracts on *both* sides of the core — Lean has `Order` in and execution events out; nautilus has order commands in and execution reports out. ADR-0092 does mention "shells produce `AnalystView[]` and feed `Fill`s back; the core returns a `Proposal`," so the triad is implicit. Make it explicit: **`AnalystView` (in), `Proposal` (out), `Fill` (back) are three host-blind contracts**, and the no-host-types leak test applies to all three.

2. **Gate polarity must be enforced structurally.** Specify `size = deterministic_max × clamp(committee_multiplier, 0, 1)`, with the committee emitting a bounded multiplier and never a size. This closes the ai-hedge-fund prompt-level leak and realizes a pre-shield in arithmetic.

3. **The money-state shape.** Adopt a fixed-point/decimal money type (nautilus); strongly consider modeling the ledger as **double-entry** so "money never appears from nowhere" is a structural invariant; permit materialized projections only as rebuildable caches gated behind a `projection == fold` property test.

4. **Contract evolution.** Commit to read-time upcasting (ADR-0091 option C), an upcaster registry shipped with the versioned core, and never mutating the log.

5. **Packaging.** Resolve the open monorepo-versus-pinned question to **monorepo-with-path-dependency**, atomic breaking changes, per-shell version pins for rollback.

**Where real systems suggest a different (or sharper) choice.** The single genuine "different choice" is structural: the gate must be a **single synchronous chokepoint on every path**, not an asynchronous risk subscriber. vn.py's event-subscriber risk module is the topology that lets a path bypass the cap — which is hermes-quant's actual two-of-four-fire-paths defect. nautilus_trader's synchronous-`RiskEngine`-before-`ExecutionEngine` topology is the correct model, and ADR-0092's single `execute()` chokepoint already aligns with it; the report's contribution is to name *why* the alternative is dangerous and to make completeness-of-coverage (every path through the gate) an explicit invariant, since an incomplete shield is the documented false-safety failure mode.

---

## Opinionated Synthesis

**Extract the shared core. The evidence does not merely permit Option D; it converges on it from four independent directions.** The core/adapter survey shows the factoring is the field's dominant pattern and that the failure it prevents is a recurrent, named disease with a known cure that hermes-quant needs. The money-state literature shows the dual-ledger bug is the dual-write problem and that a single append-only fold is its structural cure. The safe-RL shielding literature shows the gate's "silence-but-never-amplify" polarity is a formalized pattern with proven guarantees and a clean separation of concerns. And the 2025-2026 LLM-trading record shows — with frontier models losing money under honest evaluation and a measured 55.68% Sharpe decay once leakage is removed — that the charter's rails are the precise constraints the field independently recommends.

The strongest counter-argument, that a shared internal core becomes a shared shackle, is the most useful objection precisely because it sharpens the design rather than defeating it: it tells you to keep the core minimal (ledger, gate, contracts, fold — nothing else), to package it as a monorepo path-dependency rather than a cross-repo published artifact, and to treat the coupling between the two hosts' money behavior as the *feature* it is.

If the build follows five specifics, the result is not just defensible but close to best-possible for this problem. **First, three host-blind contracts** (`AnalystView`, `Proposal`, `Fill`), guarded by a no-host-types fitness test. **Second, a single append-only ledger with one fold as the sole source of truth**, ideally double-entry, with materialized projections allowed only as property-tested rebuildable caches. **Third, a single synchronous gate chokepoint on every path**, fail-closed, enforcing `size = deterministic_max × clamp(committee_multiplier, 0, 1)` so amplification is unrepresentable, with the auto-execute-versus-human decision delegated to a pluggable shell handler. **Fourth, read-time upcasting (ADR-0091 option C) over an immutable log**, with an upcaster registry versioned alongside the core. **Fifth, a monorepo-with-path-dependency** so contract changes land atomically across the core and both shells.

ADR-0092 had the architecture right. Its remaining work is not redirection but specification: name the triad, make the gate's polarity structural, pin the money-state shape, choose read-time interpretation over write-time mutation, and resolve the packaging it left open. Do that, and the money-bug class it targets becomes impossible for both hosts at once — which was the entire point.
